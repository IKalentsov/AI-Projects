# Code Review

Ревью делается по факту: файлы, сборка, тесты, git — а не по отчёту исполнителя.

## Порядок

1. Прочитать исходную постановку (`ai-tasks/<задача>/<номер>-<микро-задача>.md`).
2. Прочитать отчёт исполнителя (`<микро-задача>_report_<версия>.md`) — что заявлено.
3. Прочитать **реальные изменённые файлы** (read/grep/glob).
4. Сверить каждый пункт постановки с фактическим кодом.
5. Прогнать приёмку из постановки: сборка, затем тесты. Команды брать из `WORKFLOW.md`
   проекта, а не из памяти.
6. Проверить git-состояние — **только чтение**: `git status`, `git diff`, `git log`.
   Область ограничивать активным проектом, чтобы не тянуть дифф всего монорепозитория.
7. Сформировать вердикт.

## Что проверять

- Все пункты постановки закрыты; условие остановки достигнуто, объём не расширен.
- Сборка без ошибок **и без предупреждений** (при `TreatWarningsAsErrors=true` предупреждение
  — это ошибка сборки).
- Все тесты зелёные, включая ранее существовавшие (регрессии недопустимы).
- Не изменены `.md`-артефакты, которые исполнителю трогать запрещено (архитектура, правила,
  память проекта, чужие задачи).
- Паттерны и запреты проекта из `.dsh/AGENTS.md` соблюдены.
- Нет секретов, отладочного мусора, «заодно»-правок.

## Выход

- **Вердикт**: `ОК` или `Доработки` — одной строкой с причиной.
- **Чекпоинты** «требовалось → сделано» по каждому пункту постановки.
- **Замечания** с ровно одним решением каждое: `fix` (в этой задаче), `defer` (валидно,
  но вне объёма → отдельная задача), `reject` (неверно → обоснование фактом или правилом).
- При `fix` — отдельный файл `<микро-задача>.fixes.md`: **файл → место → что заменить**,
  чтобы исполнитель не додумывал.

## Не делать

- Не писать код за исполнителя (максимум контракт/сигнатура в fixes).
- Не доверять отчёту — проверять по коду и прогонам.
- Не запускать приложение — только сборку и тесты (запуск — зона пользователя).
- Не выполнять git-операции, меняющие состояние репозитория.
