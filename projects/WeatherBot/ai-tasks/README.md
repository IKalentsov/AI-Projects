# ai-tasks — постановки и артефакты задач

Здесь живёт весь цикл задачи: постановка → отчёт исполнителя → ревью → доработки.
Папка лежит **внутри проекта** — из рабочей области не выходим.

- Роли, цикл задачи, правила постановки, ревью и DoD — `~/.dsh/AGENTS.md` §3, §5, §6, §10.
- Процесс и git-конвенции проекта — `WORKFLOW.md`.
- Владение файлами — `.dsh/AGENTS.md` §7.

## Структура

```
ai-tasks/
├── README.md                     # этот файл
├── _templates/                   # шаблоны артефактов
│   ├── task.md                   # постановка микро-задачи
│   ├── report.md                 # отчёт исполнителя
│   ├── review.md                 # ревью архитектора
│   └── fixes.md                  # доработки по ревью
└── <номер>-<название-задачи>/    # одна папка = одна глобальная фича
    ├── <номер>-<микро-задача>.md
    ├── <микро-задача>_report_<версия>.md
    ├── <микро-задача>.review.md
    └── <микро-задача>.fixes.md
```

## Соглашения об именовании

| Артефакт | Имя файла | Кто пишет |
|----------|-----------|-----------|
| Постановка | `<задача>-<микро>.md`, например `01-01-weather-provider.md` | архитектор |
| Отчёт исполнителя | `<микро-задача>_report_<версия>.md`, например `weather-provider_report_v1.md` | исполнитель |
| Ревью | `<микро-задача>.review.md` | архитектор |
| Доработки | `<микро-задача>.fixes.md` | архитектор |

- `<номер-задачи>` — сквозной номер фичи (`01`, `02`, …).
- `<номер-микро-задачи>` — номер шага внутри фичи (`01-01`, `01-02`, …).
- Версия отчёта растёт при повторной сдаче: `_v1`, `_v2`, …
- Папка заводится под фичу, а не под слой («01-weather-provider», а не «01-backend»).

## Правила

1. **Постановка самодостаточна**: исполнитель не видит диалог архитектора и пользователя.
   Перед работой исполнитель **обязан прочитать**: `memory-bank/snapshot.md` (инвентарь и реестр
   находок), `memory-bank/activeContext.md` (где мы сейчас), `ARCHITECTURE.md` (устройство),
   `WORKFLOW.md` §2 (команды и ограничения среды), `.dsh/AGENTS.md` (правила).
   **`memory-bank/**` — только чтение**, менять нельзя.
2. В шапке постановки — маркер `Требует изменения архитектуры: да/нет`. При «да» сначала
   правится `ARCHITECTURE.md` (с подтверждением пользователя), потом пишется постановка.
3. **Никаких готовых решений**: постановка задаёт требования, контракты и критерии приёмки,
   но не содержит готового кода и псевдокода-решения. Реализацию пишет исполнитель.
4. Исполнитель пишет **только код проекта и свой `*_report_*.md`**. Остальное в `ai-tasks/`,
   а также `ARCHITECTURE.md`, `AGENTS.md`, `WORKFLOW.md`, `memory-bank/`, `README.md` —
   зона архитектора.
5. Ревью делается по фактическому коду и запущенной сборке, а не по тексту отчёта.
6. У каждой микро-задачи — **одно условие остановки**: наблюдаемый результат, при достижении
   которого исполнитель останавливается и пишет отчёт, не расширяя объём.
7. **Лимит попыток — 3** на один блокер. Дальше — стоп и честный отчёт о неудаче: что не вышло,
   сколько попыток, что пробовал, какие ошибки получил.
8. Замечания ревью закрываются решениями `fix` / `defer` / `reject`; замечание без решения
   означает, что задача не закрыта.

## Объём и проверка — правила, выведенные из провала 21.09.2026

Задача `01-02` провалилась: исполнитель выдумал несуществующий API xUnit v3, «чинил» это
массовой заменой через PowerShell, залив в исходники литеральный `\r\n`, и в итоге у него
закончился контекст на девяти файлах. Сборка после этого — 732 ошибки. Отсюда четыре правила,
обязательных для каждой постановки:

9. **Объём.** Микро-задача — это столько кода, сколько исполнитель успевает написать и проверить
   за один прогон. Ориентир: **не более 3–4 новых файлов кода**; больше — дробить.
10. **Инкрементальная проверка.** Постановка обязана требовать сборку **после первого же файла**,
    а не один раз в конце. Финальная приёмка промежуточные сборки не отменяет.
11. **Запрет массовых замен.** Постановка обязана прямо запрещать правку исходников скриптами
    и regex-проходами. Только `write` / `edit` поштучно.
12. **Стоп вместо дожима.** Если контекст заканчивается или задача «не идёт» — исполнитель
    останавливается и пишет честный отчёт. Переписывать файлы вслепую запрещено.

## Статусы (в шапке постановки)

`черновик` → `согласована` → `в работе` → `сдана` → `принята` (или `отменена`).

Статус обновляет архитектор. Исполнитель статус не меняет.
