# 🌐 Веб-разработка и внешние интеграции

> Это правило нужно, чтобы агент не выдумывал интерфейс, API или внешний сервис там,
> где их нет, и не ломал проект «красивым» решением.

## Зачем это правило нужно

В проекте **WeatherBot фронтенда нет**. Единственная «веб-часть» — технический веб-хост
(`WeatherBot.Web`) с эндпоинтами `/` и `/health` и сгенерированной документацией Scalar.
Это правило применяется, когда/если появится UI или новый внешний вызов.

Две крайности, которых избегаем:
- сделать интерфейс/интеграцию «как-нибудь, лишь бы работало»
- украшать и усложнять без пользы

## 🎨 Интерфейс (если появится)
- Дефолтно делай UI понятным и нейтральным.
- Учитывай адаптивность и доступность.
- Не добавляй маркетинговый мусор без запроса.

## 🧱 Перед реализацией
- Проверь стек проекта: сейчас это .NET 10 + Clean Architecture, без БД и без Docker.
- Уточни у пользователя must-have сценарий, прежде чем что-то придумывать.
- **Не придумывай внешний API, которого нет.**

### Мини-примеры
Неправильно:
- выдумать провайдера погоды и его эндпоинт, не спросив пользователя
- нарисовать админку-дашборд, о которой никто не просил
- завести базу данных «для истории отправок» без явного запроса
- добавить страницу/эндпоинт, которого нет в `ARCHITECTURE.md`

Правильно:
- сначала выяснить, какой источник погоды и какой формат сообщения хочет пользователь
- сначала проверить `ARCHITECTURE.md` и `memory-bank/`, что уже решено

## ✅ Проверка
- Сборка: `dotnet build WeatherBot.slnx -c Debug -m:1 --no-restore` (каталог `backend/WeatherBot`).
- Приложение запускает пользователь; агент не проверяет UI в браузере сам, а просит
  у пользователя результат, если проверка нужна.
- Не считай задачу завершённой только потому, что код «выглядит нормально».
