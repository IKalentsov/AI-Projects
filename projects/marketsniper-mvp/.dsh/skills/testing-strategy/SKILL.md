# Testing Strategy

Полная стратегия — `docs/architecture/testing-strategy.md` и `docs/frontend/testing.md`.
Здесь — рабочий порядок действий.

## Шаг 1. Выбрать уровень

| Что проверяем | Уровень | Инструмент |
|---------------|---------|-----------|
| Бизнес-правило, инвариант, расчёт | unit | xUnit v3 (backend) / Vitest (frontend) |
| Сценарий use case с подставными зависимостями | unit | + NSubstitute |
| Эндпоинт, SQL, миграции, DI, сериализация | integration | `WebApplicationFactory` + Testcontainers |
| Границы слоёв и конвенции | architecture | ArchUnitNET |
| Поведение компонента | component | Vitest + RTL |
| Фича/страница целиком | integration | Vitest + RTL + MSW |
| Ключевой пользовательский путь | e2e | Playwright |

Если сомневаешься — выбирай **самый дешёвый уровень, который реально поймает ошибку**.

## Шаг 2. Тест до кода (TDD)

1. Сформулировать ожидаемое поведение одной фразой.
2. Написать падающий тест — убедиться, что он падает **по нужной причине**.
3. Реализовать минимально достаточный код.
4. Убедиться, что тест зелёный; отрефакторить, не меняя поведение.
5. Повторить для следующего случая (включая негативный и граничный).

## Шаг 3. Backend-специфика

- Тестовый проект — исполняемое приложение (xunit.v3 4.0), `Microsoft.NET.Test.Sdk` не нужен.
- Запуск (MTP-режим, см. `backend/global.json`):

```bash
cd backend
dotnet test --solution MarketSniper.slnx -c Debug
dotnet test --project tests/MarketSniper.UnitTests/MarketSniper.UnitTests.csproj
dotnet test --solution MarketSniper.slnx -c Release -- --report-trx --results-directory ./TestResults
```

- Интеграционные тесты: один контейнер PostgreSQL на сборку (fixture), чистая БД на тест
  (Respawn), внешние HTTP — WireMock.Net, время — `FakeTimeProvider`.
- Assertions — AwesomeAssertions (`result.Should().BeSuccess()`), моки — NSubstitute.
- Никаких реальных обращений к маркетплейсам: только сохранённые фикстуры ответов.

## Шаг 4. Frontend-специфика

- RTL: искать элементы по роли и доступному имени (`getByRole('button', { name: 'Найти' })`),
  не по классам и не по `data-testid` без необходимости.
- Сеть — MSW; хендлеры переиспользуются между тестами и Storybook.
- Integration-тест: рендерим фичу с провайдерами (QueryClient, Router), отвечаем MSW,
  проверяем пользовательский сценарий и состояния (загрузка → результат → ошибка).
- E2E: только ключевые сценарии (их немного), `trace: 'on-first-retry'`, никаких `waitForTimeout`.
- Fake timers вместо ожиданий; время и случайность — детерминированы.

## Правила, которые нарушают чаще всего

1. Тест проверяет реализацию (приватные методы, внутренние вызовы) вместо поведения.
2. Один тест проверяет пять сценариев — при падении непонятно, что сломалось.
3. `Thread.Sleep`/`waitForTimeout` вместо ожидания условия.
4. Зависимость от текущей даты, порядка тестов, общего состояния БД.
5. Мок на то, что тестируется (проверяем мок, а не код).
6. Тесты «для покрытия» без осмысленных утверждений.
7. Игнорирование падающих тестов «не по теме» — они ломают доверие ко всему набору.

## Покрытие

- 70–80% на новом коде; 100% — на критичных путях (критерии, доверие, цены).
- Сгенерированный код и типы не измеряем.
- Падение покрытия ниже ориентира — повод посмотреть, что не покрыто, а не «добить процентами».

## Чек-лист самопроверки

- [ ] Уровень теста выбран осознанно (не «e2e на всё»).
- [ ] Есть позитивный, негативный и граничный сценарии.
- [ ] Тесты детерминированы и не зависят от порядка.
- [ ] Внешний мир замокан (сеть, время, случайность).
- [ ] Все тесты (включая ранее существовавшие) зелёные.
- [ ] Найденный баг закрыт тестом, который его воспроизводит.
