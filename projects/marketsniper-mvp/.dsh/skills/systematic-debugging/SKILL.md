# Systematic Debugging

Это не «давай попробуем ещё вот это». Это последовательность:
воспроизвести → собрать факты → гипотезы → проверять по одной → исправить причину → проверить регрессию.

## Когда вызывать

- Баг воспроизводится, но причина неочевидна.
- Система ведёт себя нестабильно (флаки-тесты, таймауты, гонки).
- Нужен root cause, а не маскировка симптома.
- После нескольких хаотичных попыток фикса.

## Когда НЕ вызывать

- Задача про новую фичу, а не про баг.
- Проблема уже локализована, нужна механическая правка.
- Нет способа воспроизвести — сначала собрать данные и наблюдаемость.

## Decision tree

1. **Воспроизводится?** Да → изоляция. Нет → собрать логи, условия, окружение, версии.
2. **Есть stack trace / лог ошибки?** Да → начать с первой реальной ошибки (не с последней).
   Нет → добавить наблюдаемость (структурные логи, correlation id, метрики).
3. **Где проблема: данные, логика или окружение?**
   - данные → входы, null, форматы, культура (`CultureInfo`!), схема, кодировки;
   - логика → условия, ветвления, состояние, порядок вызовов, async/await;
   - окружение → конфиги, переменные, версии, сеть, таймауты, Docker-сеть, порты.
4. **После фикса баг исчез?** Да → проверка регрессии. Нет → вернуться к гипотезам.

## Порядок диагностики

1. Воспроизвести проблему (минимальный сценарий: тест, curl, Playwright).
2. Зафиксировать ожидаемое vs фактическое.
3. Собрать логи, stack trace, контекст (запрос, данные, версия образа).
4. Изолировать участок (слой, эндпоинт, компонент).
5. Сформировать 2–3 проверяемые гипотезы.
6. Проверять по одной, меняя **только одну вещь за раз**.
7. Найти и исправить **причину**.
8. Проверить регрессию: исходный сценарий, соседний, негативный.
9. Оформить вывод.

## Специфика этого проекта

- **Бэкенд**: проверить, не теряется ли `Result` (ошибка «проглочена» и превратилась в 200);
  посмотреть логи Serilog с correlation id; `dotnet test --filter` для точечного прогона.
- **Интеграционные тесты**: Testcontainers — проверить, что контейнер реально поднялся
  (логи контейнера, здоровье), а не «тихо упал».
- **Внешние API маркетплейсов**: воспроизводить на сохранённых фикстурах, а не на живом API.
- **Фронтенд**: Network-панель, React DevTools, проверка query-ключей TanStack Query,
  состояния загрузки/ошибки, гидрация форм.
- **Docker**: «работает локально, не работает в контейнере» → переменные окружения, порты,
  сеть, права пользователя, часовой пояс, `localhost` vs имя сервиса.

## Как формулировать гипотезы

Хорошая: конкретная, проверяемая, привязанная к наблюдаемому симптому.
Плохая: «что-то не так с сервером», «возможно баг в библиотеке», «перепишем полфайла».

## Как остановить бессмысленное тыкание

- Одна правка — одна проверка.
- После каждой проверки фиксировать результат (что проверял → что вышло).
- Не прыгать к новому подозрению без вывода по предыдущему.
- Три хаотичные правки подряд → остановиться и вернуться к фактам.

## Итог дебага (формат)

- **Проблема:** что именно ломалось.
- **Гипотезы:** 2–3 версии.
- **Проверка:** что проверялось, что подтвердилось/опроверглось.
- **Причина:** реальный root cause.
- **Исправление:** что изменено (файлы).
- **Как проверено:** тест/сценарий, которым подтверждён фикс.

## Чек-лист

- [ ] Проблема воспроизведена, а не угадана.
- [ ] Симптом отделён от root cause.
- [ ] Гипотезы проверялись по одной.
- [ ] После фикса проверена регрессия и соседние сценарии.
- [ ] Добавлен тест, который ловил бы этот баг впредь.
