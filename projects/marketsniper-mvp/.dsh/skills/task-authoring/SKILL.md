# Task Authoring

Постановка пишется так, чтобы исполнитель выполнил её «от и до» без дополнительных вопросов
и без выхода за рамки задачи.

## Куда кладётся

`ai-tasks/<номер>-<название-задачи>/<номер>-<название-микро-задачи>.md`

Шаблон — `ai-tasks/_templates/task.md`. Нумерация сквозная по задаче (например `03-02`).

## Обязательная структура

0. **Требует изменения архитектуры: да / нет** — маркер согласования.
   Если «да»: сначала согласовать с пользователем правку `ARCHITECTURE.md`, внести её,
   и только потом писать постановку.
1. **Цель** — что должно получиться, 1–3 предложения, измеримо.
2. **Контекст** — где проект, стек, что уже реализовано, какие файлы существуют и как связаны.
   Исполнитель не видит наш диалог: без этого пункта он начнёт гадать.
3. **Файлы** — точные пути: что создать, что изменить (и в каком слое).
4. **Шаги** — упорядоченный план реализации.
5. **Best practice / примеры** — псевдокод, паттерны проекта, ссылки на официальную документацию.
6. **Тесты** — какие тесты и какого уровня должны появиться (unit / integration / architecture /
   Vitest / Playwright), какие сценарии покрыть, где взять фикстуры.
7. **Критерии приёмки** — проверяемый чек-лист (команды + ожидаемый результат).
8. **Что НЕ трогать** — явные запреты: файлы, слои, пакеты, поведение.

## Правила

- **Самодостаточность**: весь нужный контекст внутри файла.
- **Объём**: микро-задача выполнима в ~200k контекста исполнителя. Больше — делить.
- Постановка описывает **что** и **зачем**; **как** — только там, где есть риск ошибиться
  (псевдокод, сигнатуры, ссылки на существующие примеры в коде).
- Стек и паттерны проекта: см. `ARCHITECTURE.md`, `backend/AGENTS.md`, `frontend/AGENTS.md`.
  Не пересказывать их целиком — ссылаться и указывать только релевантное.
- Явно указывать, что исполнитель **не меняет** `ARCHITECTURE.md`, `AGENTS.md`, `docs/`,
  `ai-tasks/` (кроме своего `*_report_*.md`).
- Если задача затрагивает внешние API (маркетплейсы) — указать, как мокать их в тестах.
- В конце — напоминание: перед сдачей запустить сборку, тесты и `format/линт`.

## Признаки плохой постановки

- «Сделай красиво», «реализуй функционал поиска» без критериев.
- Ссылки на файлы, которых нет, или на «тот контроллер» без пути.
- Несколько независимых результатов в одной задаче.
- Отсутствие требований к тестам.
- Инструкции, противоречащие `ARCHITECTURE.md`.
