# Parallel Work

Параллельная работа — это не «делать всё сразу». Это:

- разделить **независимые** подзадачи;
- заранее договориться, что каждый поток отдаёт на выходе;
- собрать результаты в один вывод и сделать единую сверку.

Если контракт не определён — получится не ускорение, а хаос.

## Когда использовать

- Исследование нескольких частей кодовой базы одновременно.
- Независимые подзадачи (например: backend-контракт и frontend-форма).
- Best-of-N: несколько вариантов решения одной сложной задачи.
- Сбор внешней информации (версии пакетов, практики) — идеальный кандидат для субагентов.

## Правила

- Параллелить **только независимые** шаги; зависимые — последовательно.
- У каждого потока — свой изолированный результат: файл, отчёт, список файлов.
- Не давать двум потокам писать в одни и те же файлы без согласованного контракта.
- После параллельной работы — **единое ревью**: проверка по коду, а не по пересказу.
- Результаты субагентов проверяемы: цифры/версии/API — перепроверить в первоисточнике.

## Типичные ошибки

- Параллелить зависимые шаги (миграция БД и код, который её использует).
- Не договориться о формате результата → потом нельзя собрать.
- Принять пересказ субагента за факт без проверки.
- Запустить пять потоков там, где хватит одного.

## Чек-лист

- [ ] Параллелятся только независимые части.
- [ ] Для каждого потока понятен ожидаемый результат.
- [ ] Конфликтов по файлам нет либо они разведены контрактом.
- [ ] Есть финальная сверка результатов.
- [ ] Параллельность уменьшила время, а не добавила хаос.
