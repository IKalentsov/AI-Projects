# Frontend Design

Скилл отвечает на вопрос «что должен увидеть и сделать пользователь», а не «какие компоненты
написать». Технические правила — `frontend/AGENTS.md`, стили и темы — `docs/frontend/quality.md`,
сценарии продукта — `docs/domain/overview.md`.

## Порядок проектирования

1. **Сценарий.** Кто пользователь, что он хочет получить, что мешает ему сейчас.
   Формат: «Пользователь вводит X → получает Y → делает Z».
2. **Состояния.** До вёрстки выписать: загрузка, пусто, ошибка, успех, нет данных,
   частичный результат (часть маркетплейсов не ответила), нет доступа (когда появится авторизация).
3. **Данные.** Какие поля нужны на экране и откуда они берутся; чего в API нет
   (это задача на backend, а не «нарисуем заглушку»).
4. **Иерархия.** Что главное на экране (одно действие/один результат), что второстепенное.
5. **Компоненты.** Только после этого — раскладка на компоненты дизайн-системы.
6. **Проверка.** Пройти сценарий на мобильном и десктопе, с клавиатуры, в тёмной теме.

## Правила композиции экрана

- Один экран — одно главное действие. Всё остальное подчинено ему визуально.
- Сверху вниз: заголовок и контекст → основное действие → результат → вспомогательное.
- Поиск: поле запроса — главный элемент; фильтры — рядом или в панели, но не выше поля.
- Результат — карточки/список с одинаковой структурой: изображение, название, цена,
  продавец и его надёжность, площадка, действие «перейти».
- «Почему это предложение» (объяснение вердикта) — заметно, но не конкурирует с ценой.
- Никаких «карусельных» украшений и анимаций, мешающих чтению.

## Иерархия и типографика

- Один `h1` на страницу; уровни заголовков не перескакивают.
- Размеры и веса — только из токенов темы; ручные `text-[17px]` запрещены.
- Акцентный цвет — для главного действия и статусов; не более двух акцентов на экран.
- Цвет не единственный носитель смысла: статус дублируется текстом или иконкой.

## Тексты

- Формулировки — от лица пользователя, без технического жаргона («не удалось получить
  предложения», а не «500 Internal Server Error»).
- Кнопки — глагол + объект: «Найти предложения», «Сохранить», «Перейти на Ozon».
- Пустое состояние: что произошло + что сделать («Ничего не найдено. Попробуйте изменить запрос
  или снять фильтр по площадке»).
- Ошибка: что случилось, что делать дальше, кнопка «Повторить»; код ошибки — только
  в технических деталях.
- Единая терминология по глоссарию (`docs/domain/glossary.md`).

## Мобильный и десктоп

- Сначала мобильный сценарий: поле поиска, результаты одной колонкой, крупные цели (≥24×24 px,
  комфортно — 44×44 px).
- Десктоп: сетка 1–3 колонки в зависимости от ширины контейнера (container queries Tailwind),
  а не от ширины окна.
- Ничего важного не прячется только в hover: действия доступны по фокусу и на тач-устройствах.
- Длинные списки — пагинация или «показать ещё»; бесконечная прокрутка — только с согласования.

## Дизайн-токены и темы

- Любой цвет, отступ, радиус, тень — из токенов темы; произвольные значения запрещены.
- Тёмная тема проектируется вместе со светлой: контраст проверяется в обеих.
- Состояния интерактивных элементов: обычное, hover, focus-visible, active, disabled,
  загрузка — все шесть заданы до сдачи.

## Типичные ошибки

| Ошибка | Как правильно |
|--------|---------------|
| Макет без состояний «пусто» и «ошибка» | Все состояния проектируются заранее |
| Главное действие теряется среди второстепенных | Один явный акцент на экран |
| Технические тексты ошибок пользователю | Человеческое объяснение + действие |
| Смысл только в цвете | Дублировать текстом или иконкой |
| Бесконечная прокрутка «по умолчанию» | Пагинация; бесконечность — осознанное решение |
| Адаптив по ширине окна вместо контейнера | Container queries |
| Тёмная тема «потом» | Проектируется сразу, проверяется в обеих темах |

## Чек-лист

1. Сценарий и результат сформулированы одним абзацем.
2. Все состояния экрана описаны (загрузка, пусто, ошибка, успех, частичный результат).
3. Иерархия ясна: главное действие одно.
4. Тексты по-русски, без жаргона; кнопки — глагол + объект.
5. Мобильный и десктопный варианты продуманы; важен не hover, а доступность действия.
6. Все значения — из токенов; тёмная тема проверена.
7. Сценарий пройден с клавиатуры; фокус видим.
8. Компоненты берутся из дизайн-системы; новых «самодельных» паттернов нет.
