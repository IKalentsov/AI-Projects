# Architecture Drift Check

## Кто может менять

- `ARCHITECTURE.md` меняет только архитектор (DeepSeek V4.x) и только после подтверждения
  пользователя (для изменений, затрагивающих архитектуру).
- Исполнитель (Qwen) — read-only, строго следует документу.

## Что сверять

| Область | Источник истины в коде |
|---------|------------------------|
| Состав проектов и слоёв | `backend/MarketSniper.slnx`, `backend/src/**`, `backend/tests/**` |
| Направление зависимостей | ссылки в `.csproj` + `tests/MarketSniper.ArchitectureTests` |
| Версии пакетов и стек | `backend/Directory.Packages.props`, `backend/Directory.Build.props`, `frontend/package.json` |
| Правила анализаторов | `backend/.globalconfig`, `frontend/eslint.config.*` |
| Структура фронтенда | `frontend/apps/**`, `frontend/packages/**` |
| Инфраструктура | `docker/compose/*.yaml`, `docker/**/Dockerfile`, `.env.example` |
| Пайплайн | `.gitlab-ci.yml`, `ci/templates/*.yml` |
| Контракты API | `src/MarketSniper.Contracts/**`, сгенерированный OpenAPI/клиент |
| Схема БД | EF Core конфигурации + миграции |

## Что проверять особенно

- Нет ли ссылок «наружу» из `Domain`/`Core` (архитектурные тесты это ловят — проверить, что они есть).
- Совпадают ли версии в документации с реальными файлами (не дублировать версии в `.md` —
  ссылаться на `Directory.Packages.props`).
- Появились ли новые каталоги верхнего уровня, которых нет в структуре репозитория.
- Есть ли раздел про тестирование и соответствует ли он фактическим тестовым проектам.
- Не завелись ли «временные» решения, о которых документ молчит.

## Порядок

1. Прочитать `ARCHITECTURE.md`.
2. Собрать фактическое состояние (glob/grep/чтение конфигов).
3. Составить список расхождений: «документ говорит X → в коде Y».
4. Обновить `ARCHITECTURE.md` (и связанные файлы `docs/`) в том же прогоне, отметив дату.
5. Если расхождение означает нарушение архитектуры кодом — сообщить пользователю,
   не «подгонять» документ под код молча.

## Когда обновлять обязательно

- Изменение структуры решения, состава слоёв, контрактов API.
- Смена/добавление технологии, пакета с архитектурной ролью, инфраструктурного сервиса.
- Изменение схемы данных на уровне агрегатов.
- Изменение стратегии тестирования или пайплайна.
