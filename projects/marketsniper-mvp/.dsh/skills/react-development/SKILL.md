# React Development

Правила фронтенда — `frontend/AGENTS.md`; версии — `docs/frontend/stack.md`;
структура — `docs/frontend/project-structure.md`; данные — `docs/frontend/data-and-state.md`;
тесты — `docs/frontend/testing.md`; линт/типы/a11y — `docs/frontend/quality.md`.
Этот скилл задаёт порядок работы над фичей.

## Порядок работы над фичей

1. **Сценарий.** Сформулировать пользовательский сценарий и результат в одном абзаце.
   Если сценарий не ясен — вопрос архитектору, а не «сделаю как понял».
2. **Состояния.** Выписать состояния экрана: загрузка, пусто, ошибка, успех
   (+ «нет доступа», «частичная загрузка», если применимо). Состояния — часть задачи,
   а не «допишу потом».
3. **Контракт.** Проверить, есть ли нужные эндпоинты в OpenAPI-схеме backend.
   Если нет — задача на backend, фронт не «додумывает» API.
4. **Данные.** Определить: что серверные данные (TanStack Query), что URL-состояние (nuqs),
   что клиентское (Zustand). Ключи запросов — через фабрику ключей фичи.
5. **Слой.** Разместить код: `features/<name>/{api,model,ui,lib}`; общее — в `shared`.
   Никаких импортов из соседних фич.
6. **Компоненты.** Сначала «тупые» UI-компоненты на пропсах, затем контейнер с хуком данных.
7. **Тесты.** Unit на логику, component на взаимодействия, integration на сценарий с MSW.
   Тест пишется вместе с кодом, не после.
8. **Самопроверка.** Прогнать `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm build`
   и чек-лист ниже.

## Компоненты

- Функциональные компоненты, экспорт по имени; дефолтные экспорты запрещены
  (кроме lazy-маршрутов).
- Пропсы — явный тип `type OfferCardProps = { ... }`; дети — `children: ReactNode`.
- Компонент не делает запросов: данные приходят из хука фичи или пропсами.
- Один компонент — одна ответственность; при разрастании делить на `ui/`-части.
- Условный рендер — через ранний возврат (`if (isLoading) return <Skeleton />;`),
  без вложенных тернарников в JSX.
- Списки — стабильный `key` (id сущности), не индекс.
- Стили — только Tailwind-утилиты и токены темы; `style={{...}}` и CSS-файлы запрещены.

## Хуки

- Свой хук начинается с `use`, живёт рядом с фичей (`features/<name>/api` или `model`).
- Хук не возвращает `any`; форма возврата — объект с именованными полями.
- Загрузка данных — только `useQuery`/`useMutation`; `useEffect` для запросов запрещён.
- `useEffect` — только для синхронизации с внешними системами (подписки, DOM-API),
  с обязательной очисткой и полным списком зависимостей.
- Мемоизация (`useMemo`/`useCallback`) — только с комментарием-обоснованием: React Compiler
  включён и делает это сам.

## Данные

- Ключ запроса включает все параметры; ключи — только из фабрики фичи.
- `staleTime` задаётся осознанно (поиск/цены — 30–60 с, справочники — 30 мин).
- Мутация инвалидирует затронутые ключи в `onSettled` и возвращает промис инвалидации.
- Оптимистичные обновления — по официальному гайду; для поиска и «серьёзных» операций — нет.
- Ответ API валидируется zod-схемой до попадания в UI.
- Состояние поиска (запрос, фильтры, сортировка, страница) — в URL (nuqs), чтобы ссылка шарилась.
- Серверные данные не дублируются в Zustand или `useState`.

## Формы

- react-hook-form + `zodResolver`; схема zod — единственный источник типа формы.
- Ошибка показывается рядом с полем и связана через `aria-describedby`; тексты — по-русски,
  из схемы, без дублей в разметке.
- Кнопка отправки блокируется на время мутации; повторная отправка не создаёт дубль.
- После успешной отправки — понятная обратная связь (изменение экрана или сообщение).

## Доступность

- Семантика: `<button>` для действий, `<a>` для переходов, `<label>` для полей.
- Полный обход клавиатурой; фокус видим; модалки — из примитивов UI-кита (ловушка фокуса).
- Изображения с `alt`; кнопки-иконки с `aria-label`.
- Результаты поиска — `aria-live="polite"`; загрузка — `aria-busy`.
- Чек-лист WCAG 2.2 AA — `docs/frontend/quality.md`, §8.

## Производительность

- Новый маршрут — `React.lazy` + `Suspense` + `ErrorBoundary`.
- Тяжёлые виджеты — динамический импорт.
- Никаких «профилактических» `useMemo`; сначала измерение, потом оптимизация.
- Изображения — с `width`/`height` и `loading="lazy"`.

## Типичные ошибки

| Ошибка | Как правильно |
|--------|---------------|
| Запрос данных в `useEffect` | `useQuery` в хуке фичи |
| Ключ запроса собран строкой в компоненте | Фабрика ключей в `features/*/api` |
| Импорт хука из соседней фичи | Вынести в `entities/` или `shared/`; композиция — в `routes/` |
| `any` для быстрого прототипа | `unknown` + zod-схема |
| Фильтры в `useState` вместо URL | nuqs-парсеры |
| Оптимистичный апдейт без отката | Снапшот в `onMutate`, откат в `onError`, инвалидация в `onSettled` |
| Тест ищет элемент по `data-testid` | Запрос по роли и доступному имени |
| Снапшот разметки вместо проверки поведения | Проверять текст, роль, реакцию на действие |
| Экран без состояния «пусто» | Пустое состояние с подсказкой |
| Стили через `style={{}}` | Tailwind-классы и токены |

## Чек-лист самопроверки

1. Сценарий и все состояния экрана реализованы (загрузка, пусто, ошибка, успех).
2. Код лежит в правильном слое; cross-feature импортов нет.
3. Данные — через TanStack Query; ключи — из фабрики; мутации инвалидируют кэш.
4. Состояние поиска — в URL; ссылка воспроизводит результат после перезагрузки.
5. Формы — RHF + zod; ошибки доступны с клавиатуры и скринридеру.
6. a11y-чек-лист пройден; `aria-live` на результатах.
7. Тесты: unit + component + integration (с MSW); новых «моков модулей» нет.
8. `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm build` — зелёные.
9. Сгенерированный клиент не правился руками; схема соответствует backend.
10. В отчёте указано, что проверено вручную (какой сценарий).
