# Code Review

Ревью делается **по факту кода в репозитории**, а не по отчёту исполнителя.

## Порядок

1. Прочитать исходную постановку (`ai-tasks/.../<номер>-<микро-задача>.md`).
2. Прочитать отчёт исполнителя (`<микро-задача>_report_<версия>.md`) — что заявлено сделанным.
3. Прочитать **реальные** изменённые файлы (read/grep/glob), а не пересказ.
4. Сверить каждый пункт постановки с фактическим кодом — по чек-листу.
5. Проверить git: `git status`, `git diff` — не тронуты ли `ARCHITECTURE.md`, `AGENTS.md`,
   `docs/`, `ai-tasks/` (кроме отчёта), не добавлены ли секреты и мусор.
6. Запустить сборку: `dotnet build` (backend) / `pnpm build` + `pnpm typecheck` (frontend).
7. Запустить тесты: `dotnet test` / `pnpm test` (+ `pnpm test:e2e`, если затронут e2e-сценарий).
8. Прогнать статанализ: `dotnet format --verify-no-changes`, `pnpm lint`.
9. Сформировать вердикт.

## Что проверять

**Соответствие постановке**
- Все пункты закрыты; ничего лишнего «за компанию» не переписано.
- Контракты (DTO, эндпоинты, типы) совпадают с зафиксированными в `ARCHITECTURE.md`.

**Качество кода**
- Слои не нарушены (`Web → Infrastructure → Core → Domain → Contracts`).
- Паттерны проекта соблюдены: Result Pattern, Value Objects, snake_case в БД, тонкие контроллеры.
- Нет дублей, magic strings, «на будущее» абстракций, закомментированного кода.
- Обработка ошибок явная, с контекстом; нет проглоченных исключений.
- Производительность: нет N+1 запросов, есть пагинация, индексы под фильтры, `AsNoTracking` на чтении.
- Безопасность: нет секретов, нет SQL-конкатенации, вход валидируется, внешние вызовы с таймаутами.

**Тесты**
- Новый функционал покрыт на нужном уровне (unit / integration / architecture / e2e).
- Тесты проверяют поведение, а не реализацию; нет «тестов ради покрытия».
- **Все** тесты зелёные, включая ранее существовавшие.
- Тесты детерминированы: нет зависимости от текущего времени, сети, порядка выполнения.

**Фронтенд (если затронут)**
- Нет ручного CSS вне Tailwind-утилит и токенов; компоненты — из библиотеки проекта.
- Состояния экрана: загрузка, пусто, ошибка, нет доступа — все предусмотрены.
- Доступность: семантические роли, фокус, клавиатурная навигация, подписи у полей.
- Нет `any` и обходов типов; данные типизированы из OpenAPI-схемы.

## Выход

- **Вердикт**: `ОК` или `Доработки`.
- **Чекпоинты**: «требовалось → сделано» по каждому пункту постановки, со ссылками на файлы.
- **Замечания**: каждое получает **ровно одно** решение — `fix` (исправить в этой задаче),
  `defer` (валидно, но вне объёма → отдельная задача в `ai-tasks/` со ссылкой),
  `reject` (отклонено с обоснованием: факт, правило или ссылка).
  Замечание без решения означает, что задача не закрыта (`WORKFLOW.md` §5).
- Если нужны доработки — отдельный файл `<микро-задача>.fixes.md` с максимально конкретными
  правками: файл → место → что заменить (чтобы исполнитель не думал, а вносил).

## Pruning (чистка правил при ревью)

Если замечание обобщается шире одного диффа — перенести его в постоянное место,
в порядке приоритета: тип/схема или тест → стандарт кода в `docs/` → `ARCHITECTURE.md`/ADR →
задача в `ai-tasks/`. Дубли, устаревшие и «шумовые» формулировки удалять: одно правило —
одна авторитетная формулировка. История остаётся в git.

## Не делать

- Не писать код самому (максимум псевдокод/сниппеты в fixes).
- Не доверять только отчёту исполнителя.
- Не запускать сам сервис надолго (только сборку, тесты и, при необходимости, контейнеры для тестов).
- Не «попутно улучшать» то, что не входило в постановку — такие идеи идут в замечания.
