# Предметная область — MarketSniper

**Статус:** черновик (домен уточняется с пользователем)
**Последнее обновление:** 2026-09-10

## 1. Проблема

Покупка продуктов и товаров на маркетплейсах (Ozon, Яндекс.Маркет, Wildberries, ВкусВилл и др.)
требует ручного сравнения десятков карточек. Пользователь не может быстро ответить на вопросы:

- кто **реальный** продавец и насколько он надёжен;
- соответствует ли товар заявленному качеству (сорт, обработка, условия хранения, сроки);
- не является ли цена «приманкой», а отзывы — накрученными;
- есть ли альтернативы с лучшим соотношением «цена/качество/надёжность».

Штатные фильтры маркетплейсов дают выбор **параметров**, но не дают **проверенного ответа**
на запрос вида «хочу грецкие орехи, чтобы были чистые, свежие и от проверенного поставщика».

## 2. Что делаем

Сервис, который по свободному текстовому запросу:

1. **Понимает запрос** — превращает «хочу грецкие орехи» в структурированные критерии
   (категория, свойства, ограничения).
2. **Собирает предложения** с маркетплейсов (через API площадок, MCP-серверы и/или парсинг
   страниц — конкретный источник определяется по каждому маркетплейсу).
3. **Обогащает данные** — продавец, рейтинг, отзывы, история цены, регион, условия доставки.
4. **Проверяет по критериям качества** — в перспективе с опорой на нормативные требования
   (РосКонтроль/ГОСТ: чистота, обработка, хранение, маркировка), а также на собственные
   правила доверия к продавцу.
5. **Выдаёт результат** — только актуальные и релевантные предложения, со ссылками
   на карточки товаров и объяснением, *почему* предложение признано подходящим.

## 3. Пользователь и сценарий (MVP)

**Пользователь:** частное лицо (в перспективе — закупщик малого бизнеса).

**Основной сценарий:**

1. Открывает сайт → вводит запрос текстом.
2. Видит список предложений, отсортированных по релевантности/надёжности.
3. Открывает карточку: продавец, цена, характеристики, ссылка на маркетплейс, пояснение
   по критериям соответствия.
4. Переходит на маркетплейс для покупки.

**Сценарии второго плана (после MVP):** сохранение запросов и отслеживание цен,
подписка на снижение цены, сравнение предложений, история проверок.

## 4. Ключевые понятия (черновик)

| Понятие | Смысл |
|---------|-------|
| Поисковый запрос (Search Query) | Свободный текст пользователя + применённые критерии |
| Критерий (Criterion) | Проверяемое требование к товару или продавцу (например «срок годности ≥ 6 мес.») |
| Предложение (Offer) | Конкретный товар у конкретного продавца на конкретном маркетплейсе |
| Продавец (Seller) | Поставщик/продавец; имеет признаки надёжности |
| Маркетплейс (Marketplace) | Источник данных (Ozon, WB, Яндекс.Маркет, ВкусВилл, …) |
| Оценка доверия (Trust Score) | Итоговая оценка надёжности предложения/продавца |
| Источник данных (Data Provider) | Адаптер к API/MCP/парсеру конкретной площадки |
| Снимок данных (Snapshot) | Сохранённое состояние карточки на момент времени (цена, наличие, отзывы) |

Детальный глоссарий — `glossary.md`.

## 5. Критерии «проверенности» (что нужно уточнить)

Предварительные группы критериев:

1. **Товар**: категория, сорт/класс, состав, вес/фасовка, срок годности, условия хранения,
   маркировка, сертификаты.
2. **Продавец**: рейтинг, количество заказов, доля отзывов, возраст аккаунта, возвраты,
   юридическое лицо/самозанятый, регион.
3. **Предложение**: актуальность цены и наличия, реальность скидки (история цены),
   стоимость и срок доставки.
4. **Нормативные требования**: соответствие ГОСТ/ТР ТС, требования РосКонтроля
   (чистота, обработка, хранение) — источник данных и способ проверки требуют уточнения.

## 6. Открытые вопросы

- [ ] Формализация критериев: кто и как задаёт правила проверки (код, конфиг, БД, админка)?
- [ ] Источники данных по каждому маркетплейсу: официальный API, партнёрский API, MCP, парсинг.
      Юридические ограничения и условия использования (важно проверить до реализации).
- [ ] Как хранить историю: снапшоты в PostgreSQL, агрегаты в Redis, аналитика в отдельном хранилище?
- [ ] Что считаем «актуальным» предложением (TTL данных, частота обновления).
- [ ] Как объяснять пользователю вердикт («почему это предложение подошло»).
- [ ] Нужен ли личный кабинет и авторизация на этапе MVP (сейчас — нет).
- [ ] Монетизация и нагрузка (влияет на архитектуру: кэш, лимиты, очередь задач).

## 7. Что НЕ входит в MVP

- Покупка и оплата внутри сервиса.
- Собственный склад/логистика.
- Мобильные приложения.
- Мультиязычность.
- Авторизация и роли (закладывается место, но не реализуется).
