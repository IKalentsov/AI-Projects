# Clean Architecture — устройство бэкенда

**Последнее обновление:** 2026-09-10
Свод правил кода — `backend/AGENTS.md`. Здесь — устройство слоёв и логика размещения кода.

## Слои и зависимости

```
          ┌──────────────────────────────┐
          │  MarketSniper.Web            │  ASP.NET Core: контроллеры, middleware, DI, health
          └───────────────┬──────────────┘
                          │
          ┌───────────────▼──────────────┐
          │  Infrastructure.Postgres     │  EF Core, Dapper, миграции, репозитории
          │  Infrastructure.Redis        │  кэш, rate-limit, блокировки
          └───────────────┬──────────────┘
                          │
          ┌───────────────▼──────────────┐
          │  MarketSniper.Core           │  use cases, валидаторы, абстракции (интерфейсы)
          └───────────────┬──────────────┘
                          │
          ┌───────────────▼──────────────┐
          │  MarketSniper.Domain         │  сущности, value objects, инварианты, доменные события
          └───────────────┬──────────────┘
                          │
          ┌───────────────▼──────────────┐
          │  MarketSniper.Contracts      │  DTO и контракты, публичные наружу
          └──────────────────────────────┘
```

Зависимость направлена только вниз. Обратные ссылки запрещены и проверяются
архитектурными тестами (`TngTech.ArchUnitNET`).

## Что где живёт

| Что нужно сделать | Куда идёт код |
|-------------------|---------------|
| Новое бизнес-правило, инвариант, расчёт | `Domain` (в сущность или value object) |
| Новый сценарий (поиск, сохранение, проверка) | `Core/<Feature>/<Action>Handler.cs` |
| Валидация входных данных | `Core/<Feature>/<Action>Validator.cs` |
| Интерфейс доступа к данным | `Core/<Feature>/I<Entity>Repository.cs` |
| Реализация доступа к данным | `Infrastructure.Postgres/Repositories/` |
| Маппинг сущности в таблицы | `Infrastructure.Postgres/Configurations/` |
| Кэширование, лимиты, идемпотентность | `Infrastructure.Redis/` |
| Адаптер к маркетплейсу | `Infrastructure.<Provider>/` (по ADR при появлении) |
| HTTP-эндпоинт | `Web/Controllers/` или `Web/Endpoints/` |
| DTO запроса/ответа | `Contracts/<Feature>/` |
| DI-регистрация слоя | `DependencyInjectionExtension.cs` внутри слоя |

Правило: **новый проект в решении не создаётся без ADR.** Если код не подходит ни в один слой —
это повод обсудить архитектуру, а не завести папку «Misc».

## Поток обработки запроса

```
HTTP → Controller → Validator → Handler (Core) → Domain → Repository (Infrastructure) → PostgreSQL
                                       │
                                       └→ Result<T, Error> → маппинг в HTTP-ответ (ProblemDetails)
```

1. Контроллер принимает DTO, **не содержит логики**, вызывает use case.
2. Валидатор (FluentValidation) проверяет форму данных; бизнес-правила — в домене.
3. Handler возвращает `Result<T, Error>`; исключения — только для сбоев инфраструктуры.
4. Контроллер маппит `Result` в HTTP-код и тело; ошибки — единый формат.

## Правила, которые чаще всего нарушают

1. **Логика в контроллере.** Контроллер — переводчик HTTP ↔ use case.
2. **Domain знает про EF Core.** Атрибуты и навигационные свойства EF в домене запрещены;
   маппинг — в конфигурациях инфраструктуры.
3. **Core знает про Infrastructure.** Core объявляет интерфейсы, реализации — в инфраструктуре.
4. **Анемичная модель.** Если сущность — это набор свойств с публичными сеттерами,
   а правила лежат в сервисе, значит домен недоделан.
5. **Строки вместо типов.** `string price`, `string marketplace` — вместо `Money`, `MarketplaceId`.
6. **Возврат null вместо Result.** Отсутствие данных — это `Result`/`Error`, а не `null`.
7. **Цикломания в SQL.** Сложные выборки — в Dapper-репозитории, а не в LINQ «на три экрана».

## Проверка соблюдения

```bash
cd backend
dotnet build                              # анализаторы + TreatWarningsAsErrors
dotnet test --project tests/MarketSniper.ArchitectureTests/MarketSniper.ArchitectureTests.csproj
```

Архитектурные тесты проверяют:

- у `Domain` нет ссылок на `Infrastructure.*`, `Web`, EF Core, ASP.NET Core;
- у `Core` нет ссылок на `Infrastructure.*` и `Web`;
- `Contracts` не ссылается ни на что, кроме BCL;
- обработчики заканчиваются на `Handler`, валидаторы — на `Validator`;
- нет `async void`, нет публичных сеттеров у доменных сущностей (где применимо);
- `Web` не содержит типов из `Domain` в сигнатурах публичных эндпоинтов (только DTO).

## Architecture fitness

Принцип (`WORKFLOW.md` §8): **правило → владелец → исполняемая проверка → негативная фикстура.**
Правило, которое нельзя проверить кодом, помечается как соглашение и остаётся кандидатом
на проверку, пока не появится устойчивый шов.

**Статус:** тестовые проекты ещё не созданы, поэтому все записи ниже — план. Когда появится
постановка на тестовые проекты, эти проверки входят в её объём, включая негативные фикстуры.

| # | Правило | Владелец | Проверка | Негативная фикстура |
|---|---------|----------|----------|---------------------|
| 1 | `Domain` не зависит от инфраструктуры, EF Core и ASP.NET Core | `MarketSniper.Domain` | ArchUnitNET (architecture tests) | сборка-нарушитель `tests/Fixtures/Violators` со ссылкой Domain → EF Core, на которой то же правило обязано упасть |
| 2 | `Core` не зависит от `Infrastructure.*` и `Web` | `MarketSniper.Core` | ArchUnitNET | та же сборка-нарушитель со ссылкой Core → Infrastructure |
| 3 | `Contracts` зависит только от BCL | `MarketSniper.Contracts` | ArchUnitNET | класс-нарушитель со ссылкой на `Domain` |
| 4 | Именование: `*Handler`, `*Validator`, `I*Repository` | `MarketSniper.Core` | ArchUnitNET naming rules | тип с запрещённым именем в фикстуре |
| 5 | Нет `async void` | весь backend | ArchUnitNET + анализаторы (CA/AsyncFixer) | метод `async void` в фикстуре |
| 6 | Ошибки бизнес-логики возвращаются как `Result`, а не исключением | `MarketSniper.Core` | unit-тесты use case | тест на эталонном обработчике, бросающем исключение |
| 7 | Фронтенд: направление `shared → entities → features → routes`, без импортов между фичами | `frontend/apps/web` | ESLint `import-x/no-restricted-paths` | файл-фикстура с запрещённым импортом; CI-шаг проверяет, что линтер на нём падает |
| 8 | Списки в API отдаются только с пагинацией | `MarketSniper.Contracts` | integration-тесты эндпоинтов | запрос без `limit` обязан вернуть ошибку валидации |

Правила заполнения таблицы:

1. Одна строка — одно правило с одним владельцем. Дубли и «правила вообще» в таблицу не попадают.
2. Проверка должна входить в штатную команду (`dotnet test`, `pnpm test`), а не запускаться вручную.
3. Появилась новая граница или контракт — строка добавляется в том же прогоне, вместе с фикстурой.
4. Если правило перестало быть актуальным, строка удаляется (история остаётся в git).
