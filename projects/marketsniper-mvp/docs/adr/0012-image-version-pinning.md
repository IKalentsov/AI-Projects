# ADR 0012. Версии образов: точный пин и ручное обновление

- **Статус:** принято (заменяет политику тегов из ADR 0011)
- **Дата:** 2026-09-10

## Контекст

В сценарии деплоя есть `docker compose pull && docker compose up -d`. Если тег образа плавающий,
pull молча подтягивает более новую версию сервиса — и совместимость с нашим кодом, конфигом
и данными никто не проверял. Для stateful-сервисов это критично: путь тома PostgreSQL содержит
мажор (`/var/lib/postgresql/18/docker`), поэтому образ **без тега** (`image: postgres` — это
`latest`) при выходе следующего мажора даёт либо отказ старта, либо пустую базу.

Дополнительный риск — образы CI: обновление `trivy`/`syft` до новой версии может поменять флаги
и уронить пайплайн без единого изменения в коде.

Ранее действовало правило «фиксируем по мажорной версии, `latest` допустим для dev-инструментов»
(ADR 0011). Оно защищает от скачка мажора, но не от минорных обновлений — то есть задачу решает
наполовину.

## Решение

1. **Каждый образ пинится точной стабильной версией** — `postgres:18.6-alpine`,
   `redis:8.10.1-alpine`, `caddy:2.11.4-alpine`, `node:24.21.0-alpine`,
   `mcr.microsoft.com/dotnet/sdk:10.0.401-noble`.
2. **Запрещены**: `latest`, плавающие мажорные/линейные теги (`18-alpine`, `2-alpine`,
   `community`) и образы **без тега** — включая dev-инструменты и образы CI.
3. **Обновление версии — отдельный коммит**, вручную, после чтения release notes. Для
   stateful-сервисов дополнительно проверяется совместимость данных (мажор PostgreSQL —
   `pg_upgrade` и смена пути тома).
4. **`docker compose up` не обновляет образы.** Обновление — только явный
   `docker compose pull <сервис>` и последующий `up -d`.
5. **Об обнаружении новых версий сообщает Renovate** (dashboard + PR), а не внезапный pull.
   Обновления образов — плановая работа (раз в месяц), security-патчи — вне очереди.
6. **Проверка (fitness-функция):** CI-джоба падает, если в `docker/**` найден `:latest`,
   плавающий тег или образ без тега. Правило без проверки — это соглашение, поэтому проверка
   входит в объём задачи по пайплайну.

Канонический текст политики — `docs/architecture/infrastructure-docker.md`,
раздел «Версии образов: точный пин».

## Альтернативы

1. **Плавающий мажор** (как было): отвергнуто — именно от него уходим; минорные обновления
   приезжают незаметно.
2. **Digest-пиннинг** (`postgres:18.6-alpine@sha256:...`): строже (защищает от перезаписи тега
   в реестре), но нечитаемо, требует пересчёта при смене платформы (Windows/amd64 → linux/arm64)
   и усложняет ручное обновление. Оставляем как опцию для прод-образов, если появится требование
   supply-chain; сейчас достаточно точного тега.
3. **Всё на `latest` + `pull_policy: never`**: отвергнуто — невозможно понять, какая версия
   реально запущена, и обновление становится случайным.
4. **Фиксация версий только в проде, в dev — плавающие**: отвергнуто — локальная среда перестаёт
   соответствовать прод-контуру, а расхождение ищется дороже, чем предотвращается.

## Последствия

**Проще:** окружение воспроизводимо; «утром всё сломалось» после pull исчезает как класс;
откат версии — одна строка в compose; разбор инцидента опирается на известные версии.

**Сложнее:** обновления нужно инициировать самому; security-патчи не приезжают сами — лечится
регулярной проверкой Renovate и плановыми обновлениями; каждый пин нужно поддерживать актуальным
(в этом и смысл — обновление становится осознанным действием).

**Ограничение, которое принимаем:** версия образа меняется только вместе с отдельным коммитом,
в котором видно, что именно обновилось. Смешивать обновление образа с фичами запрещено.
