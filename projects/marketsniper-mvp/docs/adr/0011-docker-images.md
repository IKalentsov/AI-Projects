# ADR 0011. Базовые образы и стратегия сборки контейнеров

- **Статус:** принято
- **Дата:** 2026-09-10

## Контекст

Стек: ASP.NET Core на .NET 10 (Clean Architecture, EF Core, PostgreSQL, Redis) и React + Vite.
Требования: всё работает в Docker и в dev, и в prod; образы собираются в пайплайне (GitLab CI, Free);
приложение должно масштабироваться репликами; локальная разработка — Windows + Docker Desktop.
Общие правила контейнеризации — `docs/adr/0006-container-first.md`, практика —
`docs/architecture/infrastructure-docker.md`.

Ограничения, влияющие на выбор: бесплатный тир (значит, важны размер образа и скорость сборки),
необходимость healthcheck'ов в compose, отладка на этапе, когда инфраструктура ещё меняется.

## Решение

**Backend (.NET 10):**

1. Сборка — `mcr.microsoft.com/dotnet/sdk:10.0-noble`, runtime — `mcr.microsoft.com/dotnet/aspnet:10.0-noble`,
   multi-stage (стадии `build` и `runtime`; CI собирает `--target runtime`).
2. **Целевой образ после стабилизации — `aspnet:10.0-noble-chiseled-composite`**: non-root по
   умолчанию, нет shell и пакетного менеджера (меньше attack surface), фреймворк скомпилирован
   ReadyToRun (быстрее старт). **Триггер перехода (достаточно любого):** появился прод-контур
   и health-пробы перестали меняться; размер образа или время старта начали мешать
   (ориентиры: > 300 МБ, старт > 5 с); требуется сократить CVE-поверхность. До наступления
   триггера остаёмся на варианте ниже.
3. **На MVP — `aspnet:10.0-noble` + `curl` в runtime-слое.** Плата за это — десятки мегабайт и пакет
   в образе; выигрыш — работающий healthcheck в compose, shell для отладки и отсутствие
   необходимости в отдельной exec-пробе приложения. Chiseled не является «дефолтом Microsoft»:
   документация называет его «drop-in replacement», если Dockerfile не зависит от shell-скриптов.
4. В chiseled-варианте `HEALTHCHECK` — **только exec-формой** (`CMD ["/app/MarketSniper.Web", "--healthcheck"]`),
   потому что `curl`, `wget` и shell в образе отсутствуют.
5. **Trimming запрещён** (доступен только для self-contained, ломается на рефлексии EF Core и
   сериализации). `PublishReadyToRun` — только по результатам замеров: выигрыш для небольших
   приложений незначителен, размер растёт в 2–3 раза; на composite-образе фреймворк уже R2R,
   и компилировать свой код отдельно смысла мало.
6. Non-root запуск — `USER $APP_UID` (переменная определена в образах .NET 8+), файлы — `COPY --link`.

**Frontend (React + Vite):**

1. Сборка — `node:24-alpine` (Active LTS), пакетный менеджер — pnpm; зависимости ставятся по
   lockfile (`pnpm fetch` + `pnpm install -r --offline`), кэш — cache mount.
2. Runtime — `caddy:2-alpine`, `USER caddy`, порт **8080** (непривилегированный). Caddy отдаёт
   статику, делает SPA-fallback (`try_files {path} /index.html`) и сжатие `zstd br gzip`
   (brotli в официальном nginx отсутствует).
3. `VITE_*` вкомпилируются в бандл на этапе сборки; секретов там быть не может. На MVP конфигурация
   вкомпилируется, значение по умолчанию — относительный `/api/v1` (прокси маршрутизирует `/api`
   на backend, поэтому один и тот же образ работает локально и на стенде без знания адреса API).
   **Триггер перехода на runtime-подстановку** (`window.env` + `envsubst`): появление второго стенда
   с разными внешними адресами API, когда один и тот же образ должен разворачиваться в обе среды
   без пересборки. До этого дешевле собирать образ с нужным `VITE_API_BASE_URL`.

**Общее:**

1. Версии базовых образов фиксируются **точно** — политика тегов заменена
   [ADR 0012](0012-image-version-pinning.md): `latest`, плавающие мажорные теги и образы без тега
   запрещены. Выбор самих образов (noble vs chiseled, Caddy для фронта) этим ADR не отменяется.
2. Кэш слоёв обязателен: restore/pnpm install — отдельным слоем до копирования исходников,
   cache mount для пакетов, в CI — registry-кэш buildx.
3. `.dockerignore` в корне контекста исключает `bin`, `obj`, `node_modules`, `dist`, `.git`,
   `.env*`, тестовые артефакты.
4. Секреты в образ не попадают: только переменные окружения на старте или Compose `secrets:`.

## Альтернативы

1. **`alpine` для .NET**: минимальный размер, но musl вместо glibc, проблемы с ICU/tzdata и
   глобализацией (`InvariantGlobalization`), а также иная производительность — риск ради экономии
   мегабайт на MVP не оправдан.
2. **`runtime-deps` + self-contained**: не требует установленного рантайма в образе, но резко
   увеличивает размер и усложняет обновление рантайма; для framework-dependent модели (текущий выбор)
   выгоды нет.
3. **Native AOT**: лучший старт и минимальный размер, но EF Core и рефлексия накладывают
   существенные ограничения, а сборка становится долгой и хрупкой — не для MVP.
4. **`nginx-unprivileged` вместо Caddy**: знаком команде, но brotli требует отдельного модуля,
   а SPA-fallback и WebSocket настраиваются вручную; Caddy закрывает это конфигом из десяти строк.
5. **Debian/bookworm вместо Ubuntu noble**: эквивалентен по возможностям; выбран noble как основной
   вариант тегов .NET 10 в MCR.
6. **Сборка образов вне CI** (локально, с пушем в registry): быстрее на старте, но нарушает
   воспроизводимость и лишает пайплайн артефакта, привязанного к коммиту.

## Последствия

**Проще:** образы воспроизводимы и одинаковы локально и в CI; runtime-образы не содержат SDK/Node;
приложение запускается non-root; healthcheck'и работают одинаково в compose и в пайплайне; переход
на chiseled или на runtime-конфиг фронтенда не требует переписывания compose.

**Сложнее:** нужно поддерживать два варианта runtime-образа backend (noble и chiseled) и следить,
чтобы Dockerfile не «оброс» shell-скриптами; нужно регулярно обновлять базовые образы (иначе растёт
число CVE — закрывается Renovate); сборка фронтенда требует lockfile и pnpm-кэша, иначе время сборки
растёт.

**Ограничения, которые принимаем:** `curl` в MVP-образе backend — осознанное послабление
(уйдёт вместе с переходом на chiseled); trimming и AOT не используем; одна сборка фронтенда = одна
конфигурация среды (до появления потребности в промоушене образа).
