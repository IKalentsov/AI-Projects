# ADR 0009. CI/CD на GitLab CI с шаблонами в `ci/`

- **Статус:** принято
- **Дата:** 2026-09-10

## Контекст

Монорепозиторий: `backend/` (.NET 10), `frontend/` (React + Vite), `docker/` (compose, Caddyfile),
`ci/` (шаблоны). Разработка ведётся с Windows + Docker Desktop, целевой хостинг — Linux-сервер
с Docker Compose. Ограничения: **бесплатный тариф** GitLab (Free), запрет на платные подписки,
требование воспроизводимости (образы собираются в пайплайне, а не «на машине разработчика»).

Из этого следуют три вопроса: чем запускать пайплайн, как в монорепо не прогонять весь стек на каждый
коммит и как закрыть качество и безопасность бесплатными средствами.

## Решение

1. **GitLab CI** как единственный пайплайн. Точка входа — `.gitlab-ci.yml` (стадии, `workflow.rules`,
   подключение шаблонов), переиспользуемые шаблоны — `ci/templates/{dotnet,frontend,docker,security}.yml`
   через `include: local`. Состав джобов и стадий — `ci/README.md`, практика — `docs/architecture/ci-cd.md`.
2. **Избирательность в монорепо**: `rules:changes` **всегда** с `compare_to` (в MR — `refs/heads/main`,
   в основной ветке — `HEAD~1`) и с `exists` там, где джоб зависит от появления файла
   (`backend/MarketSniper.slnx`, `frontend/pnpm-lock.yaml`, `docker/*/Dockerfile`). Без `compare_to`
   на новой ветке правило всегда истинно и пайплайн делает всю работу впустую; без `exists`
   пайплайн красный ещё до появления кода.
3. **Один пайплайн на изменение**: `workflow.rules` (MR, основная ветка, тег, ручной запуск) и
   `auto_cancel.on_new_commit: interruptible` — снимают дублирующиеся прогоны.
4. **Сборка образов — buildx + Docker-in-Docker** с кэшем слоёв в registry
   (`--cache-to type=registry,mode=max`). Kaniko не используется: проект архивирован и из официальной
   документации GitLab исключён. Альтернатива при запрете privileged — rootless BuildKit или Buildah
   (меняется только джоб, Dockerfile'ы остаются те же).
5. **Тесты .NET — Microsoft.Testing.Platform** (xunit.v3), отчёты TRX + coverage в cobertura; тесты
   фронта — Vitest, e2e — Playwright. Артефакты публикуются всегда (`when: always`), иначе при падении
   не будет отчётов.
6. **Качество и безопасность — только бесплатное**: SAST (Semgrep), Secret Detection и Container
   Scanning (Trivy) из шаблонов GitLab (Free); SCA для зависимостей — `trivy fs --ignore-unfixed`
   (встроенный Dependency Scanning требует Ultimate); SBOM — Syft (CycloneDX + SPDX). Подпись
   `cosign` заготовлена, но выключена (`when: never`) до появления контура верификации.
7. **Статанализ — SonarQube Community Build** (self-hosted, профиль `sonar`) с осознанным
   ограничением: C# анализируется, но branch/PR-анализ и quality gate на MR доступны только в платных
   редакциях, поэтому гейтом на MR служат тесты, анализаторы .NET, `dotnet format` и ESLint/typecheck.
8. **Деплой** — через registry: сервер делает `docker compose pull && up -d`; окружения staging/prod
   различаются тегом образа, откат — возвратом предыдущего тега. Деплой не `interruptible`,
   запускается вручную.

## Альтернативы

1. **GitHub Actions**: зрелая экосистема и бесплатные минуты, но потребовался бы перенос репозитория
   или зеркалирование; встроенные сканеры безопасности — отдельные продукты, а не часть платформы.
   Для self-hosted GitLab выгоды нет.
2. **Jenkins**: гибкость и отсутствие лицензионных ограничений, но собственная инфраструктура,
   плагины и их обновления — несоразмерно масштабу MVP; конфигурация (Jenkinsfile + агенты) не даёт
   выигрыша против `include`-шаблонов.
3. **Только локальные проверки** (pre-commit + `dotnet test` + `pnpm test`): дешевле всего,
   но нет воспроизводимой сборки образов, нет истории артефактов, нет сканеров и нет единой точки
   правды «что считается зелёным». Отклонено: качество держится на дисциплине, а не на пайплайне.
4. **Kaniko вместо DinD**: не требует privileged, но проект архивирован и не поддерживается;
   вместо него выбраны официально рекомендованные rootless BuildKit/Buildah.
5. **Платный тир GitLab (Ultimate)** ради Dependency Scanning, DAST и гейтов на MR: отклонено
   из-за требования «без платных подписок»; потеря компенсируется Trivy/Grype и ручными проверками.

## Последствия

**Проще:** один пайплайн на весь монорепо с избирательным запуском; одинаковые образы локально и в CI;
отчёты и SBOM как артефакты; отсутствие платных зависимостей; готовый путь миграции сборки образов
(rootless BuildKit) без переписывания Dockerfile'ов.

**Сложнее:** правила избирательности нужно поддерживать в актуальном состоянии (при добавлении
каталога — добавить путь в `changes`); часть проверок безопасности требует чтения SARIF-артефактов
вместо UI; SonarQube не даёт гейта на MR; Rootless-варианты сборки требуют отдельной отладки
(`entrypoint: [""]`, права на `/proc`).

**Ограничения, которые принимаем:** пайплайн работает только на Linux-раннерах с Docker; privileged
на SaaS-раннерах считается доступным (иначе переходим на rootless); безопасность в Free-тире —
«предупреждение», а не блокировка merge; деплой остаётся ручным действием человека.
