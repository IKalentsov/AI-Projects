# ADR 0002. Clean Architecture на .NET 10

- **Статус:** принято
- **Дата:** 2026-09-10

## Контекст

Backend — ASP.NET Core-сервис с нетривиальной доменной логикой: поиск предложений, проверка
по критериям качества, оценка доверия к продавцу, интеграции с несколькими внешними
источниками (API маркетплейсов, MCP, парсинг). Логика будет меняться чаще, чем инфраструктура,
а внешние источники — заменяемыми и тестируемыми по отдельности.

Есть эталонный проект пользователя — `DirectoryService` (.NET 10, Clean Architecture, 5 слоёв,
Result Pattern, Value Objects, EF Core + Dapper, xUnit). Он написан вручную по best practice
и служит референсом подходов и качества.

## Решение

Повторяем проверенную схему: Clean Architecture, 5 слоёв, зависимости строго внутрь.

```
src/
  MarketSniper.Contracts/                  # DTO и контракты (без логики)
  MarketSniper.Domain/                     # сущности, value objects, инварианты
  MarketSniper.Core/                       # use cases, валидаторы, абстракции
  MarketSniper.Infrastructure.Postgres/    # EF Core, Dapper, миграции
  MarketSniper.Infrastructure.Redis/       # кэш, rate-limit, идемпотентность
  MarketSniper.Web/                        # ASP.NET Core: контроллеры, middleware, DI
tests/
  MarketSniper.UnitTests/
  MarketSniper.IntegrationTests/           # Testcontainers (реальная PostgreSQL/Redis)
  MarketSniper.ArchitectureTests/          # ArchUnitNET: защита границ слоёв
```

Обязательные паттерны: Result Pattern (`CSharpFunctionalExtensions`), Value Objects,
strongly-typed ID, фабрики сущностей, `snake_case` в БД, конфигурации EF Core отдельными
классами. Полный свод — `backend/AGENTS.md` и `docs/architecture/clean-architecture.md`.

Направление зависимостей проверяется **архитектурными тестами**, а не только соглашением.

## Альтернативы

1. **Vertical Slice + Minimal API**: быстрее на старте, меньше слоёв, но при росте домена
   сложнее удерживать единые инварианты и переиспользовать доменную логику между срезами.
   Допустимо как дополнение (эндпоинты группируем по фичам), но не как замена слоёв.
2. **Полный CQRS с MediatR**: даёт единообразие пайплайнов (валидация, логирование), но
   добавляет «магию» и косвенность. На MVP — избыточно; вводится точечно, если появится
   потребность в пайплайн-поведениях.
3. **Модульный монолит сразу**: разумная цель на будущее (выделение модулей `Search`,
   `Catalog`, `Trust`), но преждевременная модуляризация до появления домена вредна.

## Последствия

**Проще:** домен и бизнес-правила тестируются без БД и сети; инфраструктуру можно заменить
(например, добавить второй источник данных) без правок домена; новая функциональность
ложится в понятное место.

**Сложнее:** больше проектов и файлов; нужна дисциплина по маппингу между слоями;
риск «анемичной» модели, если правила утекают в Core вместо Domain.

**Ограничения:** слои не сокращаем «по случаю»; если для задачи не нужен отдельный
Infrastructure-проект (например, чисто доменная фича) — код идёт в существующие слои,
новые проекты не создаются без ADR.
