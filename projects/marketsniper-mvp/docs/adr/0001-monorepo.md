# ADR 0001. Монорепозиторий: backend + frontend + инфраструктура

- **Статус:** принято
- **Дата:** 2026-09-10

## Контекст

Проект разрабатывается одним человеком с привлечением AI-агентов. Backend (.NET 10), frontend
(React) и инфраструктура (Docker, CI) меняются синхронно: контракт API, схема данных и UI
тесно связаны. Нужен режим, в котором одно изменение можно провести целиком и проверить
в одном пайплайне.

## Решение

Один репозиторий `MarketSniperMVP` с каталогами верхнего уровня:

- `backend/` — решение .NET (Clean Architecture, тесты);
- `frontend/` — pnpm-монорепо (приложения и общие пакеты);
- `docker/`, `ci/` — инфраструктура и пайплайн;
- `docs/`, `ai-tasks/`, `.dsh/` — правила, документация и артефакты агентной разработки.

Контракт между частями — OpenAPI-схема, генерируемая backend'ом; клиент фронтенда
генерируется из неё (см. `docs/frontend/stack.md`).

## Альтернативы

1. **Полирепозиторий** (backend и frontend раздельно): чище права доступа и независимые
   релизы, но синхронные изменения контракта требуют двух MR и ручной синхронизации версий.
   Для одного разработчика и MVP — лишняя церемония.
2. **Монорепо с единым тулингом (Nx)**: избыточно: два стека (.NET и Node) плохо
   объединяются одним таск-раннером, а выгода проявляется на десятках пакетов.

## Последствия

**Проще:** одно изменение — один MR и один пайплайн; контракт и клиент всегда рядом;
единые правила для агентов; проще воспроизвести окружение.

**Сложнее:** пайплайн должен быть избирательным (запускать .NET-джобы только при изменениях
в `backend/`, фронтовые — в `frontend/`); репозиторий растёт; нужен `CODEOWNERS`-подобный
порядок (у нас — правила владения в `AGENTS.md`).

**Ограничения, которые принимаем:** релизы backend и frontend версионируются вместе;
разделение на отдельные репозитории — только если появится команда и независимый цикл релизов.
