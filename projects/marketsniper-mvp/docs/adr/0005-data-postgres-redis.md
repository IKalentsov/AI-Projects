# ADR 0005. Данные: PostgreSQL + Redis

- **Статус:** принято
- **Дата:** 2026-09-10

## Контекст

Профиль нагрузки: редкие записи, много чтений, значительная доля данных приходит из внешних
источников (маркетплейсы) и содержит полуструктурированные фрагменты (характеристики товара,
ответы API, результаты парсинга). Нужны: надёжное хранение домена и истории, гибкость для
«сырых» данных, дешёвый кэш внешних ответов и защита от превышения лимитов площадок.

## Решение

1. **PostgreSQL 18** — основное хранилище.
   - Реляционная модель домена, строгие инварианты, внешние ключи.
   - `jsonb` — для полуструктурированных атрибутов карточек и «сырых» ответов источников.
   - Полнотекстовый поиск (`tsvector` + GIN) на первом этапе; выделенный поисковый движок —
     только если появится реальная потребность.
   - Партиционирование по времени для исторических таблиц (снимки цен) — когда объём потребует.
2. **Redis 8** — кэш и координация.
   - Кэш ответов внешних API с TTL по типу данных.
   - Rate-limit обращений к маркетплейсам (ключи по площадке и эндпоинту).
   - Идемпотентность фоновых задач и распределённые блокировки.
   - Не является источником правды: потеря Redis не должна приводить к потере данных.
3. **Доступ к данным**: EF Core для записи и типовых чтений, Dapper — для сложных выборок
   и аналитики. Миграции — только EF Core.

## Альтернативы

1. **MS SQL Server**: сопоставим по возможностям, но `jsonb`, полнотекстовый поиск и
   бесплатность/переносимость в контейнерах у PostgreSQL удобнее; выбор площадки в пользу
   open source.
2. **Только Redis как основное хранилище**: неприемлемо — нет строгих гарантий и запросов.
3. **Добавить ClickHouse/OLAP сразу**: преждевременно; аналитика истории цен пока решается
   индексами и партиционированием PostgreSQL.
4. **Кэш в памяти процесса**: не годится при нескольких репликах backend.

## Последствия

**Проще:** кэширование и лимиты вынесены из БД; полуструктурированные данные хранятся без
миграций под каждое поле; локальная разработка — два контейнера.

**Сложнее:** два хранилища требуют дисциплины (что где живёт, инвалидация кэша,
консистентность «БД → кэш»); нужно следить за TTL и не кэшировать персональные данные.

**Ограничения, которые принимаем:** инвалидация кэша — по явным ключам и версиям
(`marketsniper:v1:...`); любые данные, попавшие в Redis, должны быть восстановимы из
PostgreSQL или внешнего источника.
