# ADR 0010. Наблюдаемость: единый транспорт OpenTelemetry/OTLP

- **Статус:** принято
- **Дата:** 2026-09-10

## Контекст

Проекту нужны логи, трейсы и метрики: внешние вызовы маркетплейсов медленные и ненадёжные, поэтому
без сквозного трейса «запрос → вызовы площадок → БД/кэш» отладка превращается в гадание. Требования:
работает локально (Windows + Docker Desktop), бесплатно, без платных подписок, ставится в тот же
compose-контур. Исторически в стеке фигурировал Seq (Serilog + Seq в dev), однако у Seq
**проприетарная лицензия** (EULA): бесплатен только тариф Individual — один пользователь
([datalust.co/pricing](https://datalust.co/pricing)). Правило проекта — «только open source».

Отдельный риск — «зоопарк транспортов»: если логи уходят одним протоколом, трейсы другим, а метрики
третьим, то смена бэкенда наблюдаемости превращается в переписывание кода приложения.

## Решение

1. **Единый транспорт — OTLP.** Приложение экспортирует логи, трейсы и метрики через OpenTelemetry
   Protocol; адресат задаётся переменными окружения (`OTEL_EXPORTER_OTLP_ENDPOINT`,
   `OTEL_EXPORTER_OTLP_PROTOCOL`, `OTEL_SERVICE_NAME`, `OTEL_RESOURCE_ATTRIBUTES`). Код приложения
   о конкретном бэкенде не знает. Логи — `Serilog.Sinks.OpenTelemetry`: `TraceId`/`SpanId`
   подхватываются из `Activity.Current`, поэтому запись в логе связана с трейсом без ручной корреляции.
2. **Dev — Aspire Dashboard** (`mcr.microsoft.com/dotnet/aspire-dashboard`, MIT), профиль
   `observability`: один контейнер, логи + трейсы + метрики в одном UI, настройки не нужны.
   Данные хранятся в памяти (перезапуск = чистый журнал), запускается без аутентификации — только
   localhost и только для разработки.
3. **Seq — опциональный профиль `seq`.** Оставлен как удобный инструмент поиска по структурным логам
   для тех, кому он нужен. Это **осознанное исключение из правила «только open source»**:
   - причина исключения: зрелый поиск по структурным логам и SQL-подобные запросы, которые
     Aspire Dashboard не заменяет;
   - границы исключения: только локальная разработка, только профиль `seq`, в деплой не попадает;
   - обязательства: при появлении второго пользователя или использовании в платном/коммерческом
     контуре требуется платная лицензия — поэтому dev-наблюдаемость по умолчанию строится на
     Aspire Dashboard, а Seq считается надстройкой.
4. **Prod-кандидат — Grafana + Loki + Tempo** (AGPLv3, open source): Grafana OSS как UI, Loki для
   логов (принимает OTLP), Tempo для трейсов, позже Mimir/Prometheus для метрик. Подключение —
   смена `OTEL_EXPORTER_OTLP_ENDPOINT`, без изменений в коде.
5. **Health-checks — часть наблюдаемости:** `/health/live` (процесс жив, без проверок зависимостей)
   и `/health/ready` (БД, Redis). Тяжёлые запросы в пробах запрещены: проба не должна нагружать
   зависимости. Пробы используются `docker compose ps`, `depends_on: service_healthy` и smoke-шагом
   пайплайна.

## Альтернативы

1. **Seq как основа наблюдаемости**: лучший UX для логов, но проприетарная лицензия и ограничение
   «один пользователь» — противоречит правилу проекта; к тому же Seq покрывает логи, но не трейсы,
   то есть всё равно потребовался бы второй инструмент.
2. **Только Grafana/Loki/Tempo в dev**: единый контур с prod-кандидатом, но четыре сервиса и
   конфигурационные файлы на локальной машине — заметная цена за отладку одного backend'а.
3. **Jaeger v2 all-in-one**: Apache-2.0, OTLP нативно, но это только трейсы; логи и метрики
   остаются без адресата, значит всё равно нужен второй компонент.
4. **Zipkin**: экспортёр Zipkin в OpenTelemetry .NET объявлен deprecated (EOL декабрь 2026) —
   тупиковая ветка ([RELEASENOTES](https://github.com/open-telemetry/opentelemetry-dotnet/blob/main/RELEASENOTES.md)).
5. **Elastic Stack**: мощно, но тяжело для локальной машины и лицензионно сложнее; для MVP
   несоразмерно.
6. **Прямая запись логов в файлы/ELK без OTel**: привязывает код к бэкенду и лишает корреляции
   логов с трейсами.

## Последствия

**Проще:** смена бэкенда наблюдаемости не трогает код; dev-контур поднимается одной командой; логи,
трейсы и метрики связаны общей корреляцией; health-checks дают единый способ проверки готовности
и в compose, и в пайплайне.

**Сложнее:** появляется зависимость от семантических конвенций и стабильности OTel-пакетов
(экспортёр периодически получает breaking changes — версии фиксируются централизованно); Seq нужно
сознательно держать «вне прода»; Aspire Dashboard не подходит для длительного хранения данных.

**Ограничения, которые принимаем:** в dev история телеметрии не сохраняется (in-memory);
Seq — исключение из правила open source, зафиксированное здесь; prod-контур наблюдаемости
появится позже и потребует отдельного решения по хранению (retention, диски, доступ).
