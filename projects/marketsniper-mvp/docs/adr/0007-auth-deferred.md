# ADR 0007. Аутентификация отложена, место зарезервировано

- **Статус:** принято
- **Дата:** 2026-09-10

## Контекст

На этапе MVP сервисом пользуется только автор проекта: личный кабинет, роли и биллинг
не нужны. При этом известно, что в будущем появятся пользователи, сохранённые запросы,
подписки на изменение цен и, возможно, внешние потребители API. Решение об аутентификации
сейчас не должно «зашиться» в код так, чтобы потом требовать переписывания.

## Решение

1. **Аутентификация не реализуется** в MVP: эндпоинты открыты, пользовательские данные
   не хранятся.
2. **Место в архитектуре резервируется заранее:**
   - в API с первого дня — версионирование (`/api/v1`) и единый формат ошибок
     (включая `401`/`403`), чтобы добавление авторизации не меняло контракты;
   - в `Web` предусмотрено место под middleware аутентификации/авторизации в конвейере
     (порядок этапов фиксируется сейчас, реализация — позже);
   - идентификация владельца данных проектируется как отдельное поле/концепт (`owner_id`),
     даже если пока всегда пустое — чтобы не менять схему задним числом;
   - секреты и параметры внешних провайдеров — через конфигурацию, не в коде.
3. **Кандидат на реализацию** — OIDC-провайдер (Keycloak как open source) либо
   ASP.NET Core Identity + JWT; выбор оформляется отдельным ADR перед реализацией.

## Альтернативы

1. **Сразу Keycloak в инфраструктуре**: даёт готовые роли и вход, но добавляет сервис,
   требующий сопровождения, при отсутствии пользователей. Преждевременно.
2. **ASP.NET Core Identity + JWT сейчас**: проще в отладке, но фиксирует модель пользователя
   до понимания продукта.
3. **Никаких заготовок**: самый дешёвый путь сейчас, но приводит к ломающим изменениям
   контрактов и схемы при добавлении авторизации.

## Последствия

**Проще:** MVP не тратит время на то, что пока не нужно; контракты API и схема данных
не потребуют ломающих изменений при добавлении входа.

**Сложнее:** нужно помнить о зарезервированных местах и не «оптимизировать» их прочь;
при появлении пользователей потребуется отдельная задача на весь контур авторизации
(включая фронтенд: guard-маршруты, обработка 401, обновление токена).

**Ограничения, которые принимаем:** до появления аутентификации сервис не выкладывается
в публичный доступ с реальными пользовательскими данными и не хранит персональные данные.
