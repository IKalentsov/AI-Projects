# ADR 0008. Стратегия тестирования: пирамида + архитектурные тесты

- **Статус:** принято
- **Дата:** 2026-09-10

## Контекст

Требование пользователя: подход TDD, покрытие тестами и на бэкенде, и на фронтенде, тесты
в пайплайне; надёжность важнее скорости «написать побольше кода». При этом тестовый контур
не должен превращаться в самоцель и тормозить разработку: тесты пишутся там, где они
защищают поведение.

## Решение

**Backend** (xUnit v3):

| Уровень | Проект | Что проверяет |
|---------|--------|---------------|
| Unit | `MarketSniper.UnitTests` | домен, value objects, валидаторы, use cases с моками |
| Integration | `MarketSniper.IntegrationTests` | API + реальная PostgreSQL/Redis (Testcontainers) |
| Architecture | `MarketSniper.ArchitectureTests` | границы слоёв, конвенции именования, запреты |

**Frontend** (Vitest + RTL + MSW + Playwright):

| Уровень | Инструмент | Что проверяет |
|---------|-----------|---------------|
| Unit | Vitest | чистые функции, парсеры, форматтеры, схемы |
| Component | Vitest + RTL | поведение компонента глазами пользователя |
| Integration | Vitest + RTL + MSW | фича/страница целиком на моках сетевого слоя |
| E2E | Playwright | ключевые сквозные сценарии (поиск → карточка → переход) |

Принципы:

1. **TDD для домена и бизнес-правил**: сначала падающий тест, затем реализация.
   Для вёрстки — тесты после стабилизации сценария (тестировать «как выглядит» бессмысленно).
2. **Тестируем поведение, а не реализацию**: никаких проверок приватных методов и внутреннего
   состояния; на фронте — queries по роли/тексту, а не по CSS-классам.
3. **Интеграционные тесты — на реальных зависимостях**: PostgreSQL/Redis поднимаются
   Testcontainers; подмена БД на in-memory не допускается, потому что не проверяет SQL,
   ограничения и миграции.
4. **Детерминированность**: никаких реальных сетевых вызовов, `sleep`, зависимости от
   текущего времени (используем `TimeProvider`/fake timers) и порядка выполнения.
5. **Внешние источники — только на фикстурах**: сохранённые ответы API/страниц в тестах,
   никаких обращений к маркетплейсам из тестов.
6. **Покрытие** — не самоцель, но минимальные ориентиры: 70–80% строк/функций на новом коде,
   100% на критичных путях (расчёт доверия, применение критериев, работа с ценами).
   Сгенерированный код и типы в покрытие не входят.
7. **Регрессия обязательна**: на каждый найденный баг сначала добавляется падающий тест,
   затем исправление.

## Альтернативы

1. **Только unit-тесты**: быстро, но не ловит проблемы миграций, DI, конфигурации, SQL.
2. **Только интеграционные (через API)**: надёжно, но медленно и плохо локализует ошибку.
3. **Snapshot-тесты UI как основа**: хрупкие, не отражают пользовательское поведение.
4. **Testcontainers вместо in-memory БД**: выбран; цена — нужен Docker в CI (он там есть).

## Последствия

**Проще:** ошибки ловятся на своём уровне; рефакторинг безопасен; CI даёт объективный сигнал.

**Сложнее:** интеграционные тесты медленнее (контейнеры) — решается параллелизацией и
кэшированием образов; нужно поддерживать фикстуры внешних API в актуальном состоянии.

Детали и команды — `docs/architecture/testing-strategy.md`.
