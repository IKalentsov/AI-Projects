# Соглашения API

**Последнее обновление:** 2026-09-10
Общие правила бэкенда — `backend/AGENTS.md`.

## Базовые принципы

- REST поверх JSON; контракты — в `MarketSniper.Contracts`.
- Версионирование в пути: `/api/v1/...` — с первого дня (см. `docs/adr/0007-auth-deferred.md`).
- Идентификаторы — строковые UUID в нижнем регистре.
- Время — ISO 8601 в UTC (`2026-09-10T12:00:00Z`); локальное время — забота клиента.
- Деньги — `{ "amount": 1234.56, "currency": "RUB" }`, не «число с плавающей точкой».
- Строки перечислений — стабильные `kebab-case` (`"wildberries"`, `"in-stock"`),
  не числовые коды и не локализованный текст.

## Ресурсы и методы

| Метод | Путь | Назначение |
|-------|------|-----------|
| GET | `/api/v1/offers` | список с фильтрами и пагинацией |
| GET | `/api/v1/offers/{id}` | карточка предложения |
| POST | `/api/v1/searches` | создать поиск (запрос) и получить результаты |
| GET | `/api/v1/searches/{id}` | состояние/результаты ранее созданного поиска |
| GET | `/api/v1/marketplaces` | список поддерживаемых площадок |
| GET | `/api/v1/health/live`, `/health/ready` | health-checks (вне `/api`-версии) |

Правила:

- Существительные во множественном числе, действия — через подресурсы (`/searches/{id}/results`).
- `GET` не меняет состояние; идемпотентные повторы `PUT`/`DELETE` допустимы.
- Долгие операции (сбор данных с площадок) — асинхронно: `POST` создаёт задачу,
  `GET` отдаёт статус; фронтенд опрашивает или подписывается.
- Массовые выборки — только с пагинацией.

## Пагинация, фильтры, сортировка

```http
GET /api/v1/offers?query=грецкие+орехи&marketplace=ozon&minPrice=500&limit=20&cursor=eyJ...
```

| Параметр | Смысл |
|----------|-------|
| `limit` | размер страницы (по умолчанию 20, максимум 100) |
| `cursor` | keyset-курсор (предпочтительно) |
| `offset` | смещение (только для небольших выборок) |
| `sort` | `price`, `-price`, `trust`, `-updatedAt` (минус — по убыванию) |

Ответ:

```json
{
  "items": [ /* ... */ ],
  "page": { "limit": 20, "nextCursor": "eyJ...", "total": 137 }
}
```

`total` может отсутствовать для больших выборок (дорогой подсчёт) — клиент обязан
ориентироваться на `nextCursor`.

## Ошибки

Единый формат на основе ProblemDetails с расширением:

```json
{
  "type": "https://marketsniper/errors/validation",
  "title": "Некорректный запрос",
  "status": 400,
  "detail": "Поле query обязательно",
  "code": "validation_error",
  "traceId": "0af7651916cd43dd8448eb211c80319c",
  "errors": { "query": ["Запрос не может быть пустым"] }
}
```

| Код | Когда |
|-----|-------|
| 400 | невалидный вход (форма запроса) |
| 404 | ресурс не найден |
| 409 | конфликт состояния (дубликат, гонка) |
| 422 | бизнес-правило нарушено (данные валидны формально) |
| 429 | превышен лимит (в т.ч. лимиты площадок) |
| 500 | внутренняя ошибка (без деталей наружу, детали — в логах по `traceId`) |
| 503 | зависимость недоступна (БД, Redis, внешний API) |

- Никаких «голых» исключений и стектрейсов в ответе.
- `code` — машиночитаемый идентификатор ошибки (стабильный, не локализуется).
- `traceId` обязателен: по нему находится запись в логах.

## Документация

- OpenAPI — `Microsoft.AspNetCore.OpenApi`, отдаётся по `/openapi/v1.json`.
- Интерактивная документация — Scalar по `/scalar/v1` (только не в Production).
- Схема — **источник правды для генерации клиента фронтенда** (`docs/frontend/stack.md`).
- Для совместимости инструментов генерации клиента фиксируем версию спецификации
  (OpenAPI 3.0/3.1) осознанно и указываем её в описании.
- Каждый эндпоинт: `summary`, описание, коды ответов, примеры запроса/ответа.

## Безопасность и эксплуатация

- Валидация входа — FluentValidation; выход — по контракту DTO (без «сырых» сущностей).
- CORS — только доверенные источники из конфигурации.
- Rate limiting — на публичных эндпоинтах, лимиты по IP/ключу.
- Correlation ID — из заголовка `X-Correlation-Id` или сгенерированный; возвращается в ответе.
- Health-checks: `/health/live` (процесс), `/health/ready` (БД, Redis, внешние зависимости).
- Логи запросов — без тел с чувствительными данными.

## Правила изменения контракта

1. Ломающее изменение = новая версия (`/api/v2`) или расширение с сохранением совместимости.
2. Добавление необязательного поля — совместимо; переименование/удаление — нет.
3. Перед изменением — обновить `Contracts`, перегенерировать клиент фронтенда, обновить тесты.
4. Контрактные изменения отражаются в `ARCHITECTURE.md` (раздел контрактов) в том же прогоне.
