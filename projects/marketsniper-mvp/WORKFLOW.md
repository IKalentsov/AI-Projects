# WORKFLOW.md — процесс работы

> **Когда читать**: перед написанием постановки, при ревью, при сдаче задачи, при изменении
> архитектуры. В остальное время достаточно `AGENTS.md`.
> **Владелец** — архитектор. Исполнитель (Qwen) читает и следует, но не меняет.
> Иерархия правил — `AGENTS.md`; устройство системы — `ARCHITECTURE.md`. Здесь — процесс.
>
> Подход адаптирован из Developer Pipeline референс-репозитория `sachkov-inside/workspace`
> (`WORKFLOW.md`) под наш цикл «постановка → исполнитель → ревью → приёмка».

**Последнее обновление:** 2026-09-10

---

## 1. Принципы работы

1. **TDD там, где он окупается**: домен, бизнес-правила, валидаторы, парсеры, расчёты —
   тест пишется до/вместе с кодом. UI-вёрстка — тестами после стабилизации сценария.
2. **Чистая архитектура**: зависимости направлены внутрь
   (`Web → Infrastructure → Core → Domain → Contracts`). Domain не знает про БД, HTTP и DI.
3. **Явный код**: минимум «магии», никаких скрытых побочных эффектов, никаких magic strings —
   константы и Value Objects.
4. **Маленькие шаги**: одна микро-задача = один проверяемый результат, выполнимый
   в контексте ~200k токенов исполнителя.
5. **Всё покрыто тестами** (см. §6). Перед сдачей задачи сборка и тесты запускаются локально.
6. **Контракты важнее реализации**: сначала фиксируем API-контракт (DTO/эндпоинты) и модель
   данных, потом реализацию.
7. **Обратная связь о рисках**: если требование противоречит best practice или ломает
   архитектуру — сказать пользователю до реализации, а не после.

---

## 2. Цикл задачи

1. **Обсуждение** — пользователь + архитектор формулируют фичу.
2. **Декомпозиция** — крупная фича режется на микро-задачи.
3. **Постановка** — файл в `ai-tasks/<номер>-<название-задачи>/` (шаблон `ai-tasks/_templates/task.md`).
   В шапке обязателен маркер: `Требует изменения архитектуры: да/нет`.
   Если «да» — сначала согласуется и правится `ARCHITECTURE.md`, потом пишется постановка (§7).
4. **Исполнение** — пользователь передаёт постановку исполнителю (Qwen / другая сессия / Cline).
5. **Отчёт** — исполнитель пишет `<микро-задача>_report_<версия>.md` (§4).
6. **Ревью** — архитектор читает постановку, отчёт и **реальные файлы**, запускает сборку и тесты,
   пишет `<микро-задача>.review.md`; при необходимости — `<микро-задача>.fixes.md` (§5).
7. **Приёмка** — пользователь смотрит результат; при доработках цикл повторяется.

Соглашения об именовании файлов задач — `ai-tasks/README.md`.

---

## 3. Постановка микро-задачи

- **Самодостаточность**: исполнитель не видит наш диалог. В постановке весь контекст:
  где проект, что уже есть, какой стек, что менять.
- **Формат**: цель → контекст → файлы (точные пути) → шаги → best practice/псевдокод →
  тесты → критерии приёмки → что НЕ трогать → **условие остановки**.
- **Объём**: ~200k контекста исполнителя. Больше — делить.
- Постановка описывает *что* и *зачем*; деталей реализации — минимум, псевдокод допустим.
- В каждой постановке явно указывать, какие тесты должны появиться.

### Одно условие остановки (обязательно)

У микро-задачи ровно **одно** условие остановки — наблюдаемый результат, при достижении
которого исполнитель обязан остановиться, написать отчёт и **не расширять объём**.

- Всё, что обнаружено «заодно» (соседний баг, рефакторинг, недостающий тест вне объёма),
  фиксируется в отчёте разделом «Отклонения и замечено» — но **не делается**.
- Если условие остановки недостижимо по внешней причине (нет данных, требование конфликтует
  с `ARCHITECTURE.md`), исполнитель останавливается **раньше** и сообщает об этом,
  а не импровизирует.
- Формулировка условия — проверяемая: «эндпоинт `POST /api/v1/searches` возвращает 200 с
  непустым списком предложений и все тесты зелёные», а не «поиск работает».

---

## 4. Отчёт исполнителя

Шаблон — `ai-tasks/_templates/report.md`. Обязательные разделы:

1. Что сделано (по пунктам постановки, без воды).
2. Изменённые файлы.
3. Тесты: команды и результат полного прогона.
4. Отклонения от постановки и замеченное «заодно» (что не делалось и почему).
5. Проблемы и вопросы, требующие решения.
6. Самопроверка по Definition of Done (§6).

Отчёт без результатов прогонов сборки/тестов не принимается.

---

## 5. Ревью и закрытие ревью

Порядок ревью (подробности — скилл `code-review`):

1. Прочитать постановку, затем отчёт, затем **реальные файлы**.
2. Сверить каждый пункт постановки с кодом.
3. Проверить git-состояние (`git status`, `git diff`) — не тронуты ли артефакты, которых
   исполнитель касаться не должен, нет ли секретов.
4. Запустить сборку, тесты, статанализ.
5. Сформировать вердикт и закрыть замечания.

### Дисциплина закрытия

Каждое замечание получает **ровно одно** решение — до того, как задача считается закрытой:

| Решение | Когда | Куда попадает |
|---------|-------|---------------|
| `fix` | замечание валидно и входит в объём задачи | `<микро-задача>.fixes.md`, затем повторный отчёт |
| `defer` | замечание валидно, но вне объёма | новая задача в `ai-tasks/` со ссылкой на замечание |
| `reject` | замечание неверно | обоснование в `review.md`: факт, правило или ссылка на источник |

- Замечание без решения = задача не закрыта. «Сырой» отчёт ревью не является результатом работы.
- Дублирующиеся, устаревшие и «шумовые» правила при ревью удаляются: **одно правило — одна
  авторитетная формулировка**. История остаётся в git.
- Если замечание обобщается шире одного диффа — оно переносится в постоянное место:
  тип/схема или тест, затем стандарт кода, затем `ARCHITECTURE.md`/ADR, затем задача в трекере.

## 6. Definition of Done

Задача считается выполненной, только если:

1. **Код компилируется** (`dotnet build` / `pnpm build`) без предупреждений
   (`TreatWarningsAsErrors=true` на бэкенде, `tsc --noEmit` на фронте).
2. **Статанализ чистый**: анализаторы .NET, ESLint, `dotnet format --verify-no-changes`.
3. **Тесты покрывают новый функционал** и разделены по уровням:
   - backend: unit (домен/логика), integration (API + БД через Testcontainers),
     architecture (запрет нарушений слоёв);
   - frontend: unit/component (Vitest + RTL), integration (страница + моки MSW),
     e2e (Playwright) — для ключевых пользовательских сценариев.
   Если существующий тест уже покрывает поведение — новый не нужен.
4. **ВСЕ тесты зелёные** (не только новые) — регрессии недопустимы.
5. **Контракты и документация актуальны**: `ARCHITECTURE.md`, `docs/`, OpenAPI-схема.
6. **Никаких секретов** в коде и в git (только `.env` / переменные окружения).
7. **Задача проверена** минимум одним реальным сценарием (smoke) или интеграционным тестом.
8. **Все замечания ревью закрыты** по дисциплине §5.

### Чек-лист перед сдачей

- [ ] Условие остановки из постановки достигнуто (и только оно — объём не расширен).
- [ ] Сборка, тесты и статанализ прогнаны, результаты приложены к отчёту.
- [ ] Обновлены документы, если менялись контракты, структура или стек.
- [ ] Секретов и отладочного мусора нет.
- [ ] Отчёт написан по шаблону, версия отчёта увеличена.

## 7. Изменение архитектуры

- Порядок: пользователь подтверждает, что задача затрагивает архитектуру → архитектор правит
  `ARCHITECTURE.md` (и связанные `docs/`) → **затем** пишется постановка.
- Маркер в шапке постановки: `Требует изменения архитектуры: да/нет`.
- Изменения структуры, контрактов, технологий и пакетов отражаются в том же прогоне,
  без «потом допишу» (скилл `architecture-drift-check`).
- ADR: принятое решение — новый файл в `docs/adr/`; замена оформляется новым ADR,
  старый получает статус «заменено (NNNN)». Удаляются только непринятые предложения.

---

## 8. Architecture fitness: правило → проверка

Принцип: **у каждого архитектурного правила есть владелец и ближайшая исполняемая проверка.**
Правило, которое нельзя проверить, — это соглашение, и оно должно быть помечено как соглашение.

| Приоритет проверки | Чем реализуется |
|--------------------|-----------------|
| Форма и типы | типы, схемы, `required`-поля, Value Objects |
| Поведение | unit-тесты домена и use case |
| Швы и зависимости | guardrails: ArchUnitNET (backend), `import-x/no-restricted-paths` (frontend) |
| Инфраструктура | интеграционные тесты (Testcontainers), проверки конфигурации |

Правила:

1. Новая или изменённая граница сопровождается **негативной фикстурой** — тестом, который
   падает, если правило нарушено. Без неё guardrail может «тихо» перестать ловить нарушения.
2. Проверки входят в штатную команду проверки проекта (`dotnet test`, `pnpm test`), а не
   запускаются «отдельно, когда вспомним».
3. Перечень действующих правил и их проверок ведётся в `docs/architecture/clean-architecture.md`
   (раздел «Architecture fitness»).
4. Правило без проверки помечается как кандидат и получает проверку, как только появляется
   устойчивый шов.

## 9. Git-конвенции

- **Git-операции выполняет только пользователь** (жёсткое ограничение — `AGENTS.md` §10).
  Ветку создаёт пользователь, push делает пользователь.
- Ветки: `develop` (рабочая), `master` (защищённая), `feature/<краткое-имя>`,
  `fix/<краткое-имя>`, `chore/<...>`.
- Коммиты — **Conventional Commits**: `feat(backend): ...`, `fix(web): ...`,
  `test(core): ...`, `docs: ...`, `chore(ci): ...`. Область — слой или приложение.
- Один коммит — одно логическое изменение; в теле объяснять «почему», а не «что».
- Merge Request: шаблон `.gitlab/merge_request_templates/Default.md`, ссылка на постановку,
  зелёный пайплайн, пройденный чек-лист DoD. В описании обязательно указывать:
  что **не тестировалось** и какие решения остаются за владельцем.
- Не коммитить сгенерированные артефакты (`bin/`, `obj/`, `node_modules/`, `dist/`).

### Помощь с сообщением коммита

Агент **предлагает** текст коммита по запросу пользователя — после того, как тот подтвердил,
что работа принята. Ветку, `add`, `commit` и `push` по-прежнему выполняет только пользователь.

Порядок:

1. **Смотреть факт, а не память.** Перед написанием — `git status`, `git diff --cached --stat`,
   `git diff --stat`, при необходимости `git diff`. Сообщение описывает то, что реально
   в индексе и рабочем дереве.
2. **Предупредить о расхождении.** Если в индексе не то, что в рабочем дереве (частичный
   `git add`), или в диффе есть посторонние файлы — сказать об этом до текста сообщения.
3. **Предложить разбивку**, если изменения разного смысла: какие файлы в какой коммит входят.
   Список файлов и команды `git add` приводит агент, выполняет — пользователь.
4. **Выдать готовый текст** блоком для копирования. Если сообщение длинное — дополнительно
   сохранить его в `ai-tasks/<задача>/commit-msg_<n>.txt`, чтобы использовать `git commit -F`.
5. **Ничего не запускать**: ни `add`, ни `commit`, ни `push` (жёсткое ограничение — `AGENTS.md` §10).

Формат сообщения:

```
<type>(<scope>): <суть, до 72 символов, повелительное наклонение>

Почему изменение нужно и что оно меняет — 2–5 строк по делу, без пересказа диффа.

- Ключевое решение или ограничение (если есть)
- Что осознанно не вошло в изменение

Refs: ai-tasks/<номер>-<задача>/<номер>-<микро-задача>.md
Not tested: <что не проверялось — или «ничего»>
```

- `type`: `feat`, `fix`, `refactor`, `test`, `docs`, `chore`.
- `scope`: `backend`, `web`, `core`, `infra`, `ci`, `docs` (слой, приложение или область).
- Тип и scope — английские, текст — русский.
- Одна задача — один коммит; изменения разного смысла — разные коммиты.
- Трейлеры `Refs:` и `Not tested:` — по необходимости; для тривиальных правок допустимо
  ограничиться заголовком и одной строкой тела.

**Запрещено** в сообщении: секреты, токены, внутренние адреса, персональные данные,
бессмысленные формулировки («WIP», «fix», «правки», «обновления»).
