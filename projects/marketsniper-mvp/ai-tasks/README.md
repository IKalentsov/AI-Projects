# ai-tasks — постановки и артефакты задач

Здесь живёт весь цикл задачи: постановка → отчёт исполнителя → ревью → доработки.
Формат и роли описаны в корневом `AGENTS.md` (§7–§8).

## Структура

```
ai-tasks/
├── README.md                     # этот файл
├── _templates/                   # шаблоны артефактов
│   ├── task.md                   # постановка микро-задачи
│   ├── report.md                 # отчёт исполнителя
│   ├── review.md                 # ревью архитектора
│   └── fixes.md                  # доработки по ревью
└── <номер>-<название-задачи>/    # одна папка = одна глобальная фича
    ├── <номер>-<микро-задача>.md
    ├── <микро-задача>_report_<версия>.md
    ├── <микро-задача>.review.md
    └── <микро-задача>.fixes.md
```

## Соглашения об именовании

| Артефакт | Имя файла | Кто пишет |
|----------|-----------|-----------|
| Постановка | `<задача>-<микро>.md`, например `03-02-search-endpoint.md` | архитектор |
| Отчёт исполнителя | `<микро-задача>_report_<версия>.md`, например `search-endpoint_report_v1.md` | исполнитель |
| Ревью | `<микро-задача>.review.md` | архитектор |
| Доработки | `<микро-задача>.fixes.md` | архитектор |

- `<номер-задачи>` — сквозной номер фичи (`01`, `02`, …).
- `<номер-микро-задачи>` — номер шага внутри фичи (`01-01`, `01-02`, …).
- Версия отчёта растёт при повторной сдаче после доработок: `_v1`, `_v2`, …
- Папка задачи создаётся под конкретную фичу, а не под слой («01-marketplace-search»,
  а не «01-backend»).

## Правила

1. **Постановка самодостаточна**: исполнитель не видит диалог архитектора и пользователя.
2. В шапке постановки — маркер `Требует изменения архитектуры: да/нет`.
   При «да» сначала правится `ARCHITECTURE.md`, потом пишется постановка.
3. Исполнитель пишет **только код проекта и свой `*_report_*.md`**. Остальные файлы
   в `ai-tasks/` — зона архитектора.
4. Ревью делается по фактическому коду и запущенным тестам, а не по отчёту.
5. Закрытая задача не удаляется: артефакты — история решений. Устаревшие постановки
   помечаются в шапке `Статус: отменена` с причиной.
6. У каждой микро-задачи — **одно условие остановки**: наблюдаемый результат, при достижении
   которого исполнитель останавливается и пишет отчёт, не расширяя объём (`WORKFLOW.md` §3).
7. Замечания ревью закрываются решениями `fix` / `defer` / `reject`; замечание без решения
   означает, что задача не закрыта (`WORKFLOW.md` §5).

## Статусы (в шапке постановки)

`черновик` → `согласована` → `в работе` → `сдана` → `принята` (или `отменена`).

Статус обновляет архитектор. Исполнитель статус не меняет.
